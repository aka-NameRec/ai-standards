# Методология evaluation structural-code-intelligence

Английская версия: [structural-code-intelligence-evaluation.md](structural-code-intelligence-evaluation.md)

Статус: методология готова, evaluation ещё не проводился. Фича `structural-code-intelligence` остаётся экспериментальной, пока этот evaluation не выполнен на реальных инженерных задачах и его результат не зафиксирован.

## Назначение

Решить по измеренным данным, входит ли structural code intelligence в рекомендуемый retrieval-стек. Правило решения:

> Принимай графовую инфраструктуру только если её измеренное улучшение на релевантных инженерных задачах оправдывает стоимость развёртывания и сопровождения.

## Конфигурации

| Рука | Конфигурация |
|---|---|
| A | только source-инструменты (grep/glob/read, без retrieval-backend'ов) |
| B | Chroma + source-инструменты |
| C | Chroma + структурный граф + source-инструменты |

Структурный backend нейтрален к реализации (Graphify или другой graph-инструмент); рука измеряет capability, а не конкретный продукт.

## Набор задач

Каждая рука прогоняется на одном и том же наборе реальных инженерных задач. Минимальное покрытие, выровненное с поведенческими сценариями реорганизации memory/retrieval:

1. Продолжить вчерашнюю незавершённую задачу (качество извлечения состояния).
2. Найти код, реализующий названную бизнес-операцию (семантическое обнаружение).
3. Изменить известный точный класс (дисциплина прямого доступа).
4. Какие модули может затронуть это изменение (анализ влияния — ключевое утверждение графа).
5. Проследить путь вызовов/зависимостей между модулями (структурный обход).

Задачи должны браться из реальной кодовой базы, достаточно большой, чтобы пропущенная зависимость была правдоподобна (проверенное референсное развёртывание: ~9k узлов / ~23k рёбер).

## Метрики на задачу

- корректность итогового ответа (проверена по исходникам и тестам)
- пропущенные зависимости (связи, которые ответ должен был назвать, но не назвал)
- ложные следы (кандидаты, на которых потрачена работа впустую)
- число открытых файлов исходников
- число вызовов инструментов
- расход токенов/контекста
- события сопровождения индекса и их стоимость (обновления, пересборки, отказы из-за устаревшего индекса)
- встреченная операционная сложность (настройка, поломки, восстановление)

## Процедура

1. Зафиксировать набор задач и ожидаемую истину (по исходникам и тестам) до запуска любой руки.
2. Прогнать руку A, затем B, затем C на идентичных состояниях задач (тот же коммит, свежий индекс).
3. Записать метрики по каждой задаче; не переносить частичные ответы между руками.
4. Посчитать агрегаты по рукам и дельту C-vs-B для зависящих от графа задач (4, 5).
5. Записать результат датированной записью решения в `docs/decisions/**` и обновить экспериментальный статус фичи.

## Критерии принятия

- C заметно лучше B на зависящих от графа задачах (меньше пропущенных зависимостей, меньше открытых файлов) без регресса на остальных;
- отказы из-за устаревшего индекса и стоимость сопровождения достаточно редки, чтобы их можно было игнорировать в ежедневной работе;
- иначе capability остаётся экспериментальной и вне рекомендуемого стека.

## Observations

- [fact] Методология измеряет capability через три руки на идентичных задачах, поэтому качество backend'а и вариативность задач не маскируют эффект.
- [fact] Принятие — результат записи решения, а не автоматический порог; управляет правило решения выше.
