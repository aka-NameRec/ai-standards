# Руководство по Basic Memory

Англоязычный оригинал: [basic-memory-usage.md](basic-memory-usage.md)

Этот документ объясняет, как использовать feature `basic-memory` из `ai-standards` в подключаемых проектах.

`basic-memory` стандартизует использование Basic Memory как Markdown-first retrieval layer, не позволяя ему превратиться в неконтролируемый источник архитектурной истины.

## Цели

Используйте `basic-memory`, когда хотите, чтобы агент или команда:

- держали durable project knowledge в Git-tracked Markdown
- эффективно искали эти знания между сессиями через Basic Memory
- различали canonical documentation и agent-managed working memory
- избегали accidental documentation drift из-за побочных эффектов индексации
- осознанно реиндексировали базу после событий в репозитории, которые могут сделать graph stale

Типовые результаты:

- меньше скрытого знания, застрявшего в chat history
- лучшее переиспользование существующих project notes и decisions
- меньше дублирующихся documentation files
- более ясные границы между reviewable truth и agent scratch space

## Что покрывает feature

Feature стандартизует shared policy для:

- использования Basic Memory как retrieval layer, а не как canonical source of truth
- разделения canonical documentation и working memory
- проверки на дублирование и противоречия перед обновлением canonical documentation
- поддержания индексируемого дерева знаний свободным от rendering inputs и machine-owned файлов
- решения о том, что заслуживает места в базе знаний, а что шум, который всё равно придётся поддерживать
- поддержания базы в форме со временем: дубли, supersession, архивация
- определения, когда достаточно filesystem auto-sync, а когда нужна явная reindex

Feature сознательно не стандартизует:

- один обязательный folder layout внутри дерева знаний
- один конкретный cloud или local deployment mode для Basic Memory
- одну универсальную schema для всех типов notes
- автоматический promotion working notes в canonical documentation

## Canonical Documentation и Working Memory

Считайте canonical documentation:

- `docs/decisions/**`
- `docs/architecture/**`
- `MODULE_CONTRACT.md`
- эквивалентные локальные artifacts, которые фиксируют принятые constraints, contracts или decisions

Считайте working memory:

- `docs/ai-memory/**`
- investigation notes
- handoff notes
- implementation gotchas
- временные findings, которые ещё развиваются

Canonical documentation должна меняться только по явному запросу пользователя. Working memory может обновляться автономно, когда это помогает сохранить полезный context.

## Границы дерева знаний

Проект Basic Memory должен указывать на выделенное дерево знаний, например `docs/`, и никогда на корень репозитория.

Корень репозитория не является knowledge base. Basic Memory индексирует всё, что может прочитать, поэтому проект на корне втягивает в граф вендорные зависимости, артефакты сборки, сгенерированные metadata и офисные документы так, будто это заметки. Качество retrieval падает, и каждый такой файл становится кандидатом на frontmatter injection.

Внутри дерева знаний любой файл — заметка. Отсюда прямое следствие для rendering inputs: файл из `local_overrides` дословно конкатенируется в сгенерированный `AGENTS.md`, поэтому frontmatter, вписанный в него индексатором, окажется посреди файла инструкций для агента. Держите такие входы вне дерева — `ai/project-rules.md`, а не `docs/ai/project-rules.md`. `ai-sync init-project` раскладывает их именно туда.

То же правило распространяется на templates, сгенерированный вывод и любой другой machine-owned Markdown.

## Frontmatter и permalinks

Basic Memory умеет записывать frontmatter во время sync. На чистом дереве знаний это желательно: именно через permalinks разрешаются адресация `memory://` и обход графа, а проект без них деградирует до обычного поиска.

Поэтому оставляйте генерацию permalinks включённой, как только в дереве остались только заметки, и примите разовый миграционный commit, добавляющий `permalink:` в существующие файлы.

Два флага отключают запись, и это fallback для legacy-дерева, которое пока нельзя сузить, а не default:

- `ensure_frontmatter_on_sync=false`
- `disable_permalinks=true`

Нужны оба сразу. Один `ensure_frontmatter_on_sync=false` не даёт добавить frontmatter в файлы без него, но файлы, у которых frontmatter уже есть, всё равно переписываются. Пара флагов также лишает адресации `memory://` — зафиксируйте этот компромисс, прежде чем его выбирать.

Учтите, что имена файлов не управляют retrieval. Заметка опознаётся по frontmatter `title`; имя файла лишь даёт fallback-заголовок для файлов, у которых его нет. Именование файлов — это house convention, и проект вправе следовать собственным правилам.

## Два жанра знания

Границу задаёт domain-driven design. **Problem space** — это бизнес как он есть: что он делает, по каким правилам работает, каким языком пользуется. Его не проектируют — его обнаруживают у экспертов предметной области и в источниках, и он остаётся истинным независимо от кода. **Solution space** — программа, построенная чтобы этому служить, и именно здесь принимаются проектные решения.

Разделение важнее всего для того, что агенту позволено менять. Когда документ смешивает жанры, агент, нашедший расхождение между документом и кодом, не может понять, что из них неверно. Для заметки из solution space привести её в соответствие с кодом обычно правильно. Для правила из problem space это катастрофа: код молча становится авторитетом в том, как устроена бухгалтерия. Разделение — это способ сказать агенту, где побеждает документ, а чинить надо код.

Жанры несут разные обязательства:

| | Problem space | Solution space |
|---|---|---|
| Род утверждения | обнаруженный факт | выбранный вариант |
| Обязано нести | источник: кто сформулировал, какой регламент или договорённость, когда подтверждено | отвергнутые альтернативы и принятые последствия |
| Меняется, когда | изменился бизнес или закон | изменилась реализация |
| Подтверждает | эксперт предметной области, регламент, договор | команда |
| Проверяется против | первоисточника | кода и тестов |

Они связаны, а не слиты. Решение `implements` правило, которому служит, поэтому рассуждение обходится с любой стороны, а правило из problem space, которое ничто не реализует, либо не построено, либо мертво.

У жанров разные каталоги, потому что путь — это первое, что агент видит, ещё не открыв файл: знание problem space в `domain/`, знание solution space в `decisions/` и `architecture/`. `type` во frontmatter говорит то же самое, но только тому, кто файл уже открыл, а самое важное правило — код никогда не является авторитетом для problem space — должно действовать в момент, когда файл берут в работу.

Дерево без `domain/` — не нарушение, а проект, чьи бизнес-правила пока живут в чьей-то голове или в трекере. Каталог появляется, когда записано первое требование.

Дробить решения между собой не нужно. Архитектурные, проектные, инструментальные и политические решения делят один формат — проект MADR ровно поэтому переименовал собственную аббревиатуру с «Markdown Architectural Decision Record» на «Markdown Any Decision Record»: границы категорий размыты, а достойно ли решение записи, решает значимость. Резать стоит между решениями и обнаруженными фактами, а не внутри решений.

## Стабильное и волатильное знание

Практика living documentation даёт вторую ось: требования и высокоуровневые цели живут дольше проектных решений, и документ, смешивающий их, наследует более короткий срок жизни. Симптом распознаётся легко — если документ приходится править после каждого рефакторинга, в него затекло волатильное знание.

Та же практика даёт правило, которое не даёт заметкам плодиться: большая часть знания, которым стоит делиться, **уже лежит в артефактах**, просто не в удобной форме. Делайте её явной там, где она живёт, вместо того чтобы пересказывать в заметку, которую потом придётся поддерживать в истинности. И держите один источник истины на факт, ссылаясь на него отовсюду, а не копируя.

## Что заслуживает места в базе знаний

Провал — не пустая база знаний. Провал — база, набитая утверждениями, которые никому не были нужны, но каждое из которых надо читать, ревьюить и поддерживать в актуальном виде.

Заметка заслуживает места, когда компетентный читатель не получит тот же ответ быстрее, открыв код. Два наблюдения об одной строке:

```
- [fact] str(digit) преобразует число в строку
- [decision] Числовые id сериализуются строками, потому что внешний API отвергает integer
```

Первое — пересказ. С ним нельзя не согласиться, оно очевидно любому, кто читает строку, и молча станет неверным, как только строка изменится. Второе — знание: переживёт рефакторинг, объясняет выбор, который без контекста выглядит ошибкой, и с ним можно спорить.

Записывать: решения вместе с отвергнутыми вариантами; правила бизнеса и то, откуда они взялись; ограничения, невидимые в коде, — юридические, договорные, эксплуатационные; отказы, которые реально случились; договорённости между людьми.

Не записывать: пересказ кода; детали реализации, которые обесценит следующий рефакторинг; собственную прозу заметки, переложенную в observations; догадки, поданные как факт. Вместо последнего называйте неопределённость неопределённостью — это само по себе стоит записи.

## Один словарь категорий

Категория наблюдения свободная — индексатор списка не фиксирует. Но вся его история про извлечение предполагает, что список зафиксировали вы: категории запрашиваемы, и `search_notes("[решение]")` полон ровно настолько, насколько единообразен словарь.

Два синонима или одна категория на двух языках поэтому вдвое урезают каждый запрос по ним, не выдавая при этом ошибки. База, где живут и `[requirement]`, и `[требование]`, на поиск любого из них вернёт половину требований и ничем не подскажет, что есть вторая.

Зафиксируйте один закрытый набор на проект, на языке самих заметок, и назовите его в правилах проекта — набору место там, а не в общем стандарте, потому что он следует за языком и предметной областью проекта. Держите его небольшим: категория, которую не отличить от соседней, будет ставиться наугад, а это стоит столько же, сколько её отсутствие.

## Задача не является предметом

Задача, issue и merge request — средства доставки. Их история уже лежит в трекере, и предметом, который кто-то потом станет искать, они не являются.

Поэтому большинство задач не порождает документации — не потому что что-то упустили, а потому что они меняют **как** продукт работает, а не **что** он обязан делать:

> Новое ТЗ расширяет существующий бизнес-функционал — добавился этап в процесс, изменилось правило о том, кому что можно.

Это знание из problem space. Оно идёт в документ, который эту логику уже описывает, и ему нужен источник. Отдельная заметка про задачу, которая это принесла, не создаётся.

> Решение было очевидным: пара моделей и сервис по уже принятому в кодовой базе шаблону.

Не пишется ничего. Ни один вариант не был отвергнут, значит и решения для записи нет, а остальное код прекрасно несёт сам.

Привычка, которой стоит избегать, — заметка на задачу, на merge request или на сессию. Она выглядит добросовестной и даёт граф, у записей которого ровно один читатель — тот, кто их написал; дальше они тихо гниют и начинают противоречить коду.

Расширять существующий документ предпочтительнее создания нового. Новый документ оправдан новым предметом, а не новой задачей.

## Как держать базу в форме

Гигиена проводится по расписанию, а не каждую сессию, и у двух слоёв разные правила.

Working memory агента можно чистить автономно: сливать дубли, разделять заметку, переросшую один концепт, убирать то, что больше не действует.

Canonical documentation работает по принципу append-and-supersede. Решение, которое больше не применяется, помечается superseded со ссылкой на замену, а не переписывается, — так остаётся читаемым исходное рассуждение и сохраняется запись о том, почему оно изменилось.

Архивировать, а не удалять. Удаление заметки выкидывает её observations и relations из графа, а значит тихо забирает контекст у каждой заметки, которая на неё ссылалась. Переносите в каталог, фиксирующий статус, сохраняя связи.

Прежде чем писать своё, берите инструменты индексатора: `bm orphans` показывает заметки без единой связи, а команды схем выводят, проверяют и сравнивают контракты полей по типам. `ai-sync doctor` закрывает структурную половину и эти проверки оставляет им.

## Изоляция рабочего пространства

Basic Memory должен быть ограничен одним проектом на рабочее пространство, чтобы retrieval возвращал только артефакты текущего проекта, а не шумную смесь из неродственных проектов.

- Ограничьте MCP-сервер одним проектом (например `bm mcp --project <project>` или эквивалентной per-workspace MCP-конфигурацией).
- Отключайте MCP-сервер Basic Memory в рабочих пространствах без проекта, чтобы запросы не падали в общий дамп по умолчанию.
- Кросс-проектный поиск оставьте для явного, осознанного действия из мета-проекта; это не режим retrieval по умолчанию.

Это удерживает knowledge-слой каждого проекта точным и предотвращает проблему «общей свалки», когда результаты смешивают артефакты неродственных проектов.

## Политика реиндексации

Обычные file edits внутри индексируемых директорий должны полагаться на стандартный filesystem sync Basic Memory.

Проверяйте status после:

- `git pull`
- `git merge`
- `git rebase`
- branch switch или checkout
- применения большого patch, который меняет много индексируемых Markdown files

Запускайте явный project reindex после:

- массовых file renames, moves или deletes внутри индексируемых директорий
- interrupted indexing или incomplete embeddings
- изменения indexed root path для проекта
- изменения permalink behavior или frontmatter-sync policy
- первой индексации существующего большого documentation tree

Предпочитайте такие operational patterns:

- `bm status --project <project>`
- `bm reindex --project <project>`
- `bm reindex --project <project> --embeddings`
- `bm reindex --project <project> --full`

Используйте самый узкий reindex, который решает обнаруженную проблему.

## Связь с другими features

- `structured-artifacts` определяет, какие Markdown artifacts считаются plans, decision records и module contracts.
- `session-hygiene` определяет, когда агент должен повторно загружать релевантный durable context между фазами или чатами.
- `conport` остаётся полезным для transient operational context и handoff storage.
- `design-first-collaboration` удерживает явными intent, boundaries и non-goals до реализации.

`basic-memory` дополняет эти features, делая Git-tracked Markdown проще для поиска и переиспользования. Он не заменяет reviewable documentation и явные human decisions.

## Пример manifest

```toml
features = [
  "conport",
  "basic-memory",
  "structured-artifacts",
  "session-hygiene",
]
```

## Практические prompt patterns

Хорошие prompts:

- `Сначала поищи в Basic Memory notes, прежде чем создавать новую design note.`
- `Проверь, не существует ли уже это решение в docs/decisions или ai-memory, прежде чем писать что-то новое.`
- `После этого merge проверь status Basic Memory и запускай reindex только если docs graph устарел.`
- `Зафиксируй этот implementation gotcha в working memory, а не в canonical documentation.`

Избегайте:

- `Перенеси всё из working notes в docs/decisions.`
- `Пусть Basic Memory переписывает repository docs как считает нужным.`
- `Делай полный reindex в каждой сессии независимо от необходимости.`

Предпочитайте:

- `Сначала используй Basic Memory для поиска, а затем обнови минимальный корректный Markdown artifact.`
