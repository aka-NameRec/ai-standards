# РЕШЕНИЕ: дизайн карты трассируемости правил

## Статус

- Принято

## Дата

- 2026-09-19

## Контекст

Фаза 2 принятой инициативы Rule Engineering (decision record
`docs/decisions/2026-09-19-adopt-rule-engineering-initiative.ru.md`) требует
устойчивой связи `rule ↔ source ↔ expected behavior ↔ eval scenarios` для
правил, на которые ссылаются evals, с удержанием IDs вне рендеренного
`AGENTS.md` и использованием их только tooling-слоем. Проверенные в
репозитории ограничения: рендерер отрезает ведущий frontmatter фрагментов
(`scripts/ai_sync.py`, `_load_fragment`), поэтому frontmatter не протекает в
рендер, — но frontmatter действует на уровне файла и не может адресовать
отдельное правило внутри фрагмента; `docs/` — knowledge tree Basic Memory, где
не-Markdown файлы получают предупреждения
`non-note-data-file-inside-knowledge-tree`; `registry.toml` — каталог
features/stacks по модульному контракту `ai-sync`.

## Решение

Трассируемость правил живёт в отдельном корневом `rule_map.toml`:

- по таблице на правило с ключом-стабильным ID (`<PREFIX>-<NNN>`, например
  `RE-001`); ID никогда не переиспользуется для другого правила, а вывод
  правила из обращения сохраняет его ID зарезервированным;
- каждая запись связывает ID с `fragment` (путь под `fragments/`), `section`
  (заголовок внутри фрагмента, якорящий нормативный текст), `behavior`
  (однострочная формулировка ожидаемого наблюдаемого поведения) и `scenarios`
  (IDs eval-сценариев из спецификации `ai-standards-evals`, issue #18; пусто,
  пока фаза 3+ не породит сценарии);
- policy-тесты в `tests/test_rule_map.py` — детерминированная валидация карты:
  корректные уникальные IDs, существование фрагментов и секций, корректность
  behaviors и ссылок на сценарии, отсутствие IDs в рендеренном `AGENTS.md`;
- заполнено `RE-001`–`RE-006` по фрагменту feature `rule-engineering`.

## Почему так

- Единый дом tooling-метаданных на конфигурационном слое (рядом с
  `registry.toml`, вне knowledge tree) оставляет IDs доступными eval-tooling,
  но структурно не способными попасть в рендер.
- Якоря-заголовки дают стабильные, проверяемые человеком места без inline-
  маркеров в прозе.
- Policy-тесты делают саму карту проверяемой — то же требование наблюдаемого
  поведения, которое стандарт предъявляет правилам.

## Рассмотренные альтернативы

- Frontmatter файлов фрагментов: только на уровень файла — не адресует
  отдельные правила; к тому же зарезервирован дизайном для штампов
  knowledge-base индексера.
- IDs прямо в рендеренной прозе: протекли бы в контекст каждого включившего
  проекта — против требования фазы 2.
- Секция внутри `registry.toml`: смешивает каталог features/stacks из
  модульного контракта `ai-sync` с per-rule метаданными.

## Последствия

- Польза: каждое правило, покрытое evals, получает стабильный проверяемый
  тестами якорь; сценарная работа фазы 3+ и `ai-standards-evals` (#18) может
  ссылаться на конкретные IDs; вопрос «какими тестами покрыто это правило?»
  решается по карте.
- Издержки: каждое новое eval-правило нужно добавлять в карту; переименование
  заголовка требует обновления карты (ловится тестами); формату IDs сценариев
  нужно согласование с runner (отложено в #18).

## Затрагиваемые модули

- `rule_map.toml` (новый, корень репозитория)
- `tests/test_rule_map.py` (новые policy-тесты)
- `fragments/process/rule-engineering.md` (упоминается, без изменений)

## Инварианты и ограничения

- IDs правил никогда не попадают в `AGENTS.md` (закреплено policy-тестом).
- ID никогда не переиспользуется для другого правила.
- Карта остаётся на конфигурационном слое, вне knowledge tree `docs/`.
- Семантика исполнения сценариев остаётся за `ai-standards-evals` (issue #18);
  карта только резервирует ссылки.

## Проверки

- `uv run pytest tests/test_rule_map.py` (пять policy-тестов)
- `uv run ai-sync render --project-root .` остаётся идемпотентным
- `uv run ruff check` / `uv run mypy scripts/` чисты
