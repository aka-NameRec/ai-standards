# DECISION: add-code-review-feature

Англоязычный оригинал: [2026-08-06-add-code-review-feature.md](2026-08-06-add-code-review-feature.md)

## Статус

Accepted

## Дата

2026-08-06

## Контекст

Обычный, ничем не уточнённый запрос «code review» в чате в проекте, инициализированном через `ai-standards`, должен надёжно запускать ревью по собранным правилам проекта, с результатом, оформленным одинаково при каждом запуске.

В `ai-standards` уже была фича `review-lenses`, но она задокументирована как policy с явной активацией: она ожидает запрос, называющий сам workflow, либо per-tool adapter вроде навыка `simplify-review`. К тому же она покрывает только cleanup-ориентированную модель Reuse/Quality/Efficiency, а не корректность или соответствие собственным архитектурным, error-handling и стековым правилам проекта.

Переиспользуемого правила, которое соединяло бы триггер на естественном языке с формой отчёта, идентичной между запусками, инструментами и моделями, не было. Отчёту дополнительно нужны: ссылка на задачу, когда она существует; короткое прозаическое вступление о том, что и как изменилось; severity и названное нарушенное правило у каждой находки, опирающиеся на реальную локацию в файле; явный выбор между выводом в чат и сохранением в файл; и полная локализация под язык чата.

Пока фича оставалась невыпущенной, появился второй источник: рукописный workflow ревью, который ежедневно использовался для подготовки описаний pull request по каждому репозиторию. Он независимо пришёл к тому же отчёту из двух жанров — прозаическое вступление об изменении, за ним находки — и к одному отчёту на репозиторий. При этом он нёс три вещи, которых у фичи не было: раздел `Verification` с тем, что реально запускалось и, что важнее, что не запускалось; раздел `Dependencies` для изменений, дотягивающихся до другого репозитория; и политику для узкого класса правок, которые ревьюер может безопасно сделать по ходу, — она фиче нужна была в любом случае, потому что маркер ✅ для исправленных находок определён, а когда правка разрешена, не сказано нигде. Влить это до релиза дешевле, чем выпустить две формы и сводить их потом.

## Решение

`ai-standards` добавляет `code-review` как opt-in process feature (`fragments/process/code-review.md`, зарегистрирована в `registry.toml`).

Feature разделяет два вида содержимого, и именно это разделение — несущая часть решения:

- **Переиспользуемые стандарты ревью, сформулированные как правила.** Что проверять и в каком приоритете; что делает находку пригодной к сообщению (конкретная локация в файле, названное нарушенное правило, утверждение, проверенное по коду, а не по diff, достаточная детальность, никаких выдуманных правил, никакого раздувания); как обходиться с проблемами, существовавшими до diff; отчёт как поведение по умолчанию с ограниченным исключением для правок, безопасность которых устанавливается чтением.
- **Форма отчёта, заданная один раз заполненным примером.** `templates/code-review-report.md` — образец ревью, определяющий разделы, их порядок, поля каждой находки и маркеры серьёзности. Прозаические ограничения, описывающие формат, заменены самим форматом. Файл раскладывается в каждый проект с включённой фичей как `.ai-standards/code-review-report.md` через agent-agnostic канал `INFRA_TEMPLATES`, который уже обслуживает `chroma` — поэтому adapter в `tooling.agents` не нужен, а фрагменту достаточно на него сослаться.

Вокруг примера — восемь коротких рабочих правил: маркеры серьёзности (🔴 блокирует, 🟡 стоит исправить, 🔵 по желанию, ✅ исправлено, с хвостом `→ fixed:` или `→ left as-is:` в самой строке находки); полная локализация под язык чата при бессловесных маркерах-исключениях; вывод в чат по умолчанию и в файл только по запросу; обработка более позднего «пришли отчёт ещё раз» как переклассификации уже найденных находок, а не повторного ревью с нуля; ссылка на задачу, предпочитающая полную ссылку голому id всегда, когда база трекера известна — из сессии, из собственных правил проекта или из записи `tracker_url` в `[metadata]` манифеста, которая уже рендерится в шапку собранного файла, так что адрес остаётся у организации, применяющей стандарт, а не в этом репозитории; по одному отчёту на репозиторий, когда задача затрагивает несколько, потому что у каждого репозитория свой pull request; `Verification`, заполняемый по факту запущенного и называющий непроверенное; и `Dependencies`, остающийся только тогда, когда изменение дотягивается до другого репозитория.

Пять проверяемых аспектов получают пять разделов вместо трёх, чтобы `Reuse`, `Efficiency` и `Quality` находились по собственным заголовкам, а не делили один. Корректность и конвенции по-прежнему идут первыми — именно это защищала прежняя группировка.

Переиспользование и конвенции, которые изменение соблюло правильно, называются в `How It Was Done` прозой, а не находками. У находки есть маркер, а маркер обязан означать невыполненную работу, иначе просмотр одних маркеров перестаёт отвечать на вопрос, что осталось сделать.

Отдельное правило `Fixing While Reviewing` ограничивает маркер ✅: правка без спроса допустима только тогда, когда её безопасность устанавливается чтением, и с явным списком по обе стороны — переводы, опечатки, мусор в `.gitignore` и локальные рассогласования с одной; миграции, lock-файлы, зависимости, конфигурация сборки, публичные контракты, индекс git, рефакторинг и всё, требующее прогона тестов, с другой. Рефакторинг стоит на стороне «только сообщить» намеренно: перестройка кода — решение автора, а не дефект, который устраняет ревьюер.

Feature включена в self-hosted manifest и стартовый манифест проекта и поставляется с bilingual usage-документацией, так что подключаемые проекты принимают её обычной manifest composition без tool-specific настройки.

## Почему

- закрывает пробел добавлением, вписывающимся в существующую архитектуру manifest/registry/fragment, а не tool-specific хаком
- сохраняет триггер и форму отчёта tool-neutral: они живут в собранном `AGENTS.md`/`CLAUDE.md`, поэтому все читающие этот файл инструменты ведут себя одинаково и adapter в `tooling.agents` не нужен
- держит формат строгим, но дешёвым в поддержке: один заполненный пример вместо спецификации, пересказанной в нескольких документах
- не трогает `review-lenses`, поэтому проекты, использующие только проходы чистки, не получают изменения поведения

## Рассмотренные альтернативы

### Влить триггер в `review-lenses`

Отклонено. Три downstream-проекта используют `review-lenses` без `code-review`; слияние выдало бы им авто-триггер на естественном языке и обязательную форму отчёта, которых там никто не просил, молча изменив задокументированный контракт на следующем же рендере. Дублирование, которое действительно стоило убрать, — это формат, пересказанный в нескольких файлах внутри `code-review`, а не существование двух фич; слияние лечило бы не ту дупликацию.

### Выпустить Claude-specific авто-вызываемый Skill вместо правила в `AGENTS.md`

Отклонено как основной механизм. Skill достаёт только до инструментов, у которых есть механизм навыков, и требует записей в `tooling.agents`, которые downstream-манифесты в основном оставляют пустыми; инструменты, читающие только `AGENTS.md`, потеряли бы фичу. Skill остаётся разумным будущим дополнением ради экономии контекста, но правило обязано работать и без него.

### Оставить формат на project-local overrides

Отклонено. Рекомендации самого репозитория отправляют правила, нужные одному проекту, в локальные дополнения, но этот формат нужен всем проектам организации; растаскивание его по per-project overrides воссоздало бы ровно то дублирование, ради устранения которого репозиторий и существует.

### Задавать формат прозаическими ограничениями вместо заполненного примера

Отклонено после того, как версия на ограничениях выросла примерно до сорока строк императивов («always this section order», «never open with findings», «state None found.») и всё равно оставила пробелы. Её многократно переписывали, а поскольку та же спецификация пересказывалась во фрагменте, обоих usage-гайдах и обоих decision record, каждая правка формулировок стоила пяти синхронных редактирований и дважды ломала тест. Публичные рекомендации по промптингу ревью-агентов также сообщают, что заполненный пример превосходит zero-shot ограничения. Теперь пример — единственный источник истины.

### Встроить заполненный пример во фрагмент

Отклонено, как только выяснился путь доставки. Инлайн стоит примерно двадцати шести строк always-on контекста в каждой сессии каждого проекта с включённой фичей и не покупает ничего, чего не даёт раскладка: `INFRA_TEMPLATES` гейтится только по фиче, поэтому файл попадает в проект без объявления адаптеров. Раскладка действительно вносит два сценария отказа, и оба обработаны, а не проигнорированы: проект, не выполнивший `sync-templates`, оставил бы указатель висящим — поэтому во фрагменте есть краткий fallback-порядок и требование сообщить об отсутствии файла; а локально изменённую копию sync пропускает как unmanaged, что зафиксировано ниже как принятый риск расхождения.

### Оставить рукописный per-repository workflow второй, отдельной формой

Отклонено. Остались бы два документа, претендующие на один триггер и одну работу, различающиеся списком разделов и наличием маркеров у находок, — и ничто не решало бы, какой из них выдаст конкретная сессия. Оба уже сошлись на двух жанрах в одном отчёте и на одном отчёте на репозиторий, а это самая дорогая часть дизайна; оставшиеся различия были не разногласиями, а взаимными пробелами. Слияние до релиза стоит одной ревизии невыпущенной формы. Отказ от слияния стоит сведе́ния потом, уже против проектов, начавших вставлять одну из двух форм в pull request.

### Сообщать удачные решения изменения находкой с ✅

Отклонено, хотя называть правильное переиспользование стоит, и теперь это требуется. ✅ определён как исправленная находка, а вердикта в отчёте нет именно ради того, чтобы просмотр маркеров отвечал, что осталось сделать. ✅, который иногда значит «исправлено», а иногда «здесь и так было хорошо», это ломает. Похвала — проза, и её место в `How It Was Done`.

### Полностью подавлять находки вне diff

Отклонено как слишком грубое. Молчаливое отбрасывание всех находок вне scope — первая нормализация рекомендации Codex/Cloudflare «не вменять diff'у» — выбрасывает реальный сигнал, который у ревьюера уже есть. Сообщение с пометкой `(pre-existing)` сохраняет сигнал, не обвиняя текущее изменение, а явное сужение scope это отключает.

## Последствия

### Плюсы

- голый запрос «code review» ведёт себя одинаково между сессиями, инструментами и моделями
- формат определён в одном месте, поэтому его изменение — правка одного файла
- не требуется tool-specific adapter или настройка
- чисто композируется с `review-lenses`, сохраняющей свою активацию и scope
- отчёт одновременно годится как описание pull request, поэтому один проход обслуживает и ревью, и передачу работы
- что проверено, а что нет, сказано прямо, а не оставлено на догадку

### Минусы или цена

- в репозитории появляется ещё один process feature и пара usage-гайдов для поддержки
- форма отчёта стала отдельным разложенным файлом, поэтому включение фичи теперь требует `ai-sync sync-templates` вдобавок к `render`; при пропуске этого шага фрагмент деградирует до fallback-порядка
- проект может отредактировать свою копию, и тогда sync пропустит её как unmanaged; это позволяет осознанную локальную кастомизацию ценой молчаливого расхождения с общей формой
- подключаемые проекты всё равно должны явно включить фичу через манифест; конвейер рендеринга ничего не навязывает
- девять разделов дают более длинный отчёт, чем пять; конвенция «Не найдено.» держит пустые в одну строку, но даже тривиальное изменение выдаёт страницу
- разрешение хоть каких-то правок требует границы, которая является списком, а не принципом, а у списков есть края, в которых агент может ошибиться

## Инварианты и ограничения

- форма отчёта определена файлом `templates/code-review-report.md` и больше нигде. Полный список разделов перечисляют ровно два места, оба во фрагменте и оба неизбежны: fallback-порядок для проекта, не разложившего шаблон, и таблица локализации. Правило может обращаться к отдельному разделу по имени; перечислять форму вне фрагмента нельзя
- отчёт — поведение по умолчанию; правка сверх того, что разрешает `Fixing While Reviewing`, требует явного запроса пользователя, и рефакторинг в это разрешение не входит никогда
- находка без конкретной локации в файле или без привязки к правилу не должна сообщаться
- утверждение о коде вне diff читается по этому коду прежде, чем будет написано
- ссылка на задачу никогда не выдумывается; при её отсутствии строка опускается, а URL выводится только когда его база действительно известна
- мультирепозиторное изменение никогда не даёт один общий отчёт; по одному на репозиторий, потому что один отчёт идёт в один pull request
- pre-existing проблема сообщается и помечается, а не молчаливо отбрасывается, если пользователь не сузил scope
- ✅ ставится только по-настоящему исправленным находкам; сознательно пропущенная сохраняет цветной маркер
- то, что изменение сделало правильно, идёт в `How It Was Done` и никогда не оформляется помеченной находкой, чтобы маркеры продолжали означать невыполненную работу
- `Verification` называет и запущенное, и незапущенное; неупомянутая проверка читается как пройденная, поэтому молчание здесь является дефектом
- `Dependencies` убирается для замкнутого изменения, а не заполняется заглушкой
- весь отчёт следует одному языку в рамках сессии; бессловесные маркеры — единственное исключение
- путь сохранения по умолчанию не должен неявно превращать отчёт в canonical documentation
- feature должна оставаться tool-neutral и не менять активацию или scope `review-lenses`

## Проверка

- `registry.toml` содержит feature `code-review`
- рендеринг с включённой `code-review` включает фрагмент, его правило активации и указатель на `.ai-standards/code-review-report.md`
- `sync-templates` раскладывает шаблон отчёта в проект с включённой `code-review` даже при пустом `tooling.agents` и не раскладывает при выключенной фиче
- usage-гайды существуют на английском и русском и не пересказывают формат
- README документирует feature на обоих языках
- self-hosted `AGENTS.md` успешно рендерится с включённой фичей
- каждый раздел заполненного примера присутствует и в fallback-порядке, и в таблице локализации, что проверяется тестом
