# РЕШЕНИЕ: standards-update-workflow

Английский источник истины: [2026-08-28-standards-update-workflow.md](2026-08-28-standards-update-workflow.md)

## Статус

Принято

## Дата

2026-08-28

## Контекст

Запрос на обновление из подключаемого проекта — «обнови ai-standards до последней версии, доступной в его репозитории» — был недоопределён в четырёх местах. Нигде не было сказано, какой чекаут считать последним исходником. Пин `ai_standards_version` в `ai.project.toml` не обновлялся ни одной командой: при расхождении рендер лишь добавлял комментарий в шапку и рендерил тот исходник, с которым запущен, поэтому развёртывание могло молча уехать с версии, которую декларировало. Новые фичи не приезжали, потому что рендер берёт фичи строго из списка `features` манифеста — корректно в рамках opt-in модели (см. решение о размещении гейта той же даты), — но означало, что обновление ничего не анонсировало и ничего не включало. И ни одно правило не просило агента показать, что изменилось, и подтвердить, что включать, — агент импровизировал.

Требования сопровождающего: запрос должен оставаться коротким; последняя версия — это новейший релиз репозитория ai-standards на GitHub; новые фичи должны анонсироваться с описаниями и включаться только после явного подтверждения, уместного для стеков проекта; а бутстрап-случай — развёртывание старше самого скилла — должен быть описан в release notes.

## Решение

Скилл `update-ai-standards` определяет всю процедуру обновления; запрос остаётся одной фразой. Скилл развёртывается с каждым развёртыванием ai-standards, объявившим агентов в `[tooling].agents`, — без фиче-гейта, потому что он обслуживает сам ai-standards, а не процесс проекта.

Процедура: сравнить развёрнутую версию (пин `ai_standards_version`, с откатом к шапке собранного файла) с последним релизом обслуживаемого чекаута (метаданные `standards_source` в манифесте, если есть, иначе чекаут, известный сессии); молча обновить включённые фичи; анонсировать фичи, чей `since` в `[feature_meta]` файла `registry.toml` новее развёрнутой версии, — по одной строке, с рекомендацией относительно стеков проекта и ссылкой на гид; задать один вопрос, что включать; применить только подтверждённые фичи, перевести пин и проверить результат через `render`, `sync-templates`, `check` и `doctor` до отчёта.

Сопутствующие изменения: `[feature_meta]` в `registry.toml` фиксирует релиз, представивший каждую фичу, — дайджест становится механическим; `ai-sync check` падает при дрейфе пина, `render`/`update` предупреждают, `doctor` сообщает `standards-version-drift`; release notes несут инструкции по бутстрапу, чтобы развёртывание старше скилла могло применить обновление вручную один раз.

## Обоснование

- промпт — интерфейс, скилл — контракт: голая фраза должна давать определённую процедуру, так же как голый запрос «code review»
- молчание — тот отказ, который чинится: расходящийся пин и фичи, о которых проект не может знать, становятся видимыми вместо скрытых
- шаг подтверждения примиряет обновления с opt-in моделью — обновление никогда не меняет то, на что проект дал согласие, а один вопрос на обновление — минимальная усталость, которая это гарантирует
- безусловное развёртывание скилла снимает проблему курицы и яйца: инструмент, обслуживающий развёртывания, должен присутствовать в каждом развёртывании, которое он обслуживает

## Рассмотренные альтернативы

### Указывать в промпте путь к скиллу в репозитории

Отклонено. Скилл резолвится в окружении агента после развёртывания; путь в чекаут ai-standards превращает промпт обратно в инструкцию импровизировать, которая работает, только если чекаут досягаем. Легитимный бутстрап-случай покрыт release notes.

### Включать новые фичи по умолчанию при обновлении

Отклонено. Это противоречит opt-in модели и решению о размещении гейта той же даты: обновление, включающее фичи, — ровно то безмолвное изменение поведения, которое потребители не могут заметить. Один вопрос подтверждения даёт минимальную усталость при явном согласии.

### Рендерить фрагмент активации в `AGENTS.md`

Отклонено на сейчас. Активаторные фразы несёт описание самого скилла, адаптеры уже развозятся через `sync-templates`, а постоянный фрагмент стоил бы контекста в каждой сессии каждого проекта за процедуру, которая выполняется между релизами.

### Разбирать CHANGELOG как единственный источник обнаружения новых фич

Отклонено как единственный механизм. Разбор прозы хрупок; `[feature_meta].since` делает дайджест детерминированным, а CHANGELOG остаётся прозаическим источником для заметных добавлений вне фич.

## Последствия

### Польза

- одна фраза обновляет развёртывание, с фиксированной процедурой и видимым diff'ом поведения
- дрейф пина невозможно пропустить: `check` падает, `render`/`update` предупреждают, `doctor` сообщает
- новые возможности доходят до потребителей в момент обновления, а не требуют заранее читать release notes

### Компромиссы

- каждое развёртывание с заявленными агентами получает ещё по одному адаптеру на агента; проекты, которые не обновляются, платят только диском
- значения `feature_meta.since`, указывающие на невышедшую версию, нужно сверить с фактическим номером релиза во время `bump-version`

### Дальнейшие шаги

- продвинуть гейт обнаружения модульных контрактов в фичу `module-contract-gate` (размещение принято решением той же даты); скилл обновления затем анонсирует её старым развёртываниям ровно так, как задумано

## Observations

- [decision] Скилл update-ai-standards развёртывается на всех заявленных агентах без фиче-гейта, потому что обслуживает сам ai-standards.
- [decision] Новые фичи анонсируются при обновлении по `[feature_meta].since` и включаются только после одного явного подтверждения; ничего не включается по умолчанию.
- [fact] `ai-sync check` падает, пока `ai_standards_version` расходится с фактически используемым исходником стандартов; `render` и `update` предупреждают, `doctor` сообщает `standards-version-drift`.
