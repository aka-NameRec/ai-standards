# РЕШЕНИЕ: release-versioning-human-decided

Английская версия: [2026-10-12-release-versioning-human-decided.md](2026-10-12-release-versioning-human-decided.md)

## Статус

Принято

## Дата

2026-10-12

## Контекст

В задачах #23 и #24 версия репозитория поднималась по-задачно: `bump-version
save` выполнялся внутри каждого набора изменений (2.8.0 для #23, 2.9.0 для
#24), хотя релиз не выпускался. Пользователь заметил это после слияния #24:
версия растёт только при выполнении релиза; момент релиза определяет человек;
в релиз могут входить несколько задач. Оба бампа были откачены до 2.7.0, а
следующие релизы (2.8.0, затем 2.8.1) выпущены явно по приказу пользователя.

## Решение

1. `bump-version save` выполняется только как часть релиза, явно заказанного
   пользователем, — никогда внутри фичевой задачи, какой бы завершённой она
   ни была.
2. Между релизами завершённая работа накапливается в секции `[Unreleased]`
   CHANGELOG; версионные секции по задачам не создаются.
3. В момент релиза версия выбирается один раз, по SemVer над накопленными
   изменениями с предыдущего релиза, и ожидающие записи CHANGELOG
   группируются под секцией релиза.
4. Поток релиза сохраняется: `bump-version save` → релизный коммит в `main`
   → push → `bump-version tag` → GitHub release.

## Почему так

- Номер версии — обещание о выпущенном состоянии; подъём по задаче изобретает
  несуществующие релизные состояния.
- Объединение — право релиза: несколько задач (#23, #24) вышли вместе в
  2.8.0, что позадачные бампы исказили бы.
- Момент релиза отражает готовность к ревью и упаковке — это знание
  мейнтейнера, а не агента.

## Рассмотренные альтернативы

### Позадачные бампы версии (отклонённое поведение)

Отклонено: порождало невыпущенную 2.9.0 и искажало бы объединённые релизы;
каждый бамп также переписывает пины манифестов и перерисовывает `AGENTS.md`,
подразумевая выпущенное состояние.

### Полностью автоматические релизы при слиянии в `main`

Отклонено: слияние в `main` само по себе выполняется по приказу человека
(см. правило приземления `autonomous-task-run`); автоматизация релиза
ставила бы механический гейт поверх человеческого.

## Последствия

### Польза

- Один подъём версии на реальный релиз, чистый SemVer над объединёнными
  задачами.
- `[Unreleased]` — единственная зона накопления; release notes режутся
  напрямую из неё.

### Компромиссы

- Долго живущая секция `[Unreleased]` требует периодической гигиены
  (секции 2.6.0–2.8.1 восстановлены в этой же сессии), чтобы выпущенные
  записи не оставались неатрибутированными.

## Наблюдения

- [decision] Версия растёт только в момент релиза; момент релиза определяет
  человек; релиз может объединять несколько задач.
- [fact] Позадачные бампы задач #23 (2.8.0) и #24 (2.9.0) были откачены до
  корректного выпуска 2.8.0; откат и гигиена истории CHANGELOG зафиксированы
  в записи задачи 25.
