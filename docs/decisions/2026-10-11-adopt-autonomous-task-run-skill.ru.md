# РЕШЕНИЕ: adopt-autonomous-task-run-skill

Английская версия: [2026-10-11-adopt-autonomous-task-run-skill.md](2026-10-11-adopt-autonomous-task-run-skill.md)

## Статус

Принято

## Дата

2026-10-11

## Контекст

Issue #24 зафиксировало повторяющуюся практику задач #22–#23: пользователь
одобряет план и поручает агенту работать автономно до завершения, слить в
`main` по стандарту, сначала зафиксировать знания и коммитить без одобрения
каждого коммита. Инварианты живут в `autonomy-boundaries` и
`session-hygiene`, но процедуру — entry gate, слайс-цикл, сверку с
требованиями, порядок приземления — каждый раз собирали из чата. В ходе
обсуждения issue пользователь закрепил пять дополнительных нормативных
пунктов: верифицируемый task spec (в проектах с ADR — в форме ADR) с
критерием приёмки у каждого требования; слайсованный план с проверкой до
старта; сверку слайса с требованиями по его завершении; требования как
абсолютную константу запуска (без дополнения, изменения и
переинтерпретации); остановку с подробным отчётом при любом неустранимом
противоречии или блокере.

## Решение

1. Принимается навык `autonomous-task-run`, гейт на feature
   `autonomy-boundaries`, деплой для codex, cursor, claude и kilo.
2. Entry gate, процедура, stop-условия, completion report и не-цели навыка
   следуют кандидату из issue #24, проверенному через Rule Engineering;
   worksheet с вердиктами по каждому пункту —
   `docs/artifacts/2026-10-11-autonomous-task-run-authoring.md`.
3. Приняты две словесные адаптации: артефакт требований назван «task spec (в
   проектах с ADR — в форме ADR)» ради переносимости, а правило коммитов
   снабжено прецедентной оговоркой — инструкция работать автономно и есть
   стоящее одобрение commit-потока, что сохраняет совместимость навыка с
   общим правилом одобрения коммитов.
4. Нормативное содержимое прослежено как `ATR-001`–`ATR-007` в
   `rule_map.toml`, с контрактами поведенческих сценариев `ATR-001`,
   `ATR-002` и trigger set `TRG-003` в `docs/scenarios/` (исполнение —
   `ai-standards-evals`, issue #18).
5. Фрагмент `autonomy-boundaries` получает одну строку-указатель на
   деплоированный навык; остальное его нормативное содержимое не меняется.

## Почему так

- Слой skill загружает процедуру ровно в момент появления триггер-фразы,
  вместо всегда загруженной процедурной детализации (Context Architecture).
- Пять пунктов пользователя закрывают два режима отказа, которыми реально
  рисковали запуски #22–#23: дрифт требований в длинном запуске и молчаливая
  подгонка формулировки требований ради сходимости.
- Для процедуры «проверка только отчётом» невозможна; контракты сценариев
  дают процедуре её поведенческую форму валидации.

## Рассмотренные альтернативы

### Вшить процедуру в всегда загружаемый фрагмент autonomy-boundaries

Отклонено: задачная операциональная детализация нарушает инвариант control
plane (CA-004); фрагмент держит инварианты, навык — шаги.

### Продолжать собирать запуск из чата каждый раз

Отклонено: запуск #23 потребовал от пользователя заново проговорить весь
договор (коммиты без одобрения, слияние в main, сначала фиксация знаний) —
ровно то повторение, для устранения которого существует навык.

### Гейт на новую отдельную feature

Отклонено: `autonomy-boundaries` уже владеет правилами долгого исполнения и
естественен как гейт; новая feature добавила бы поверхность без смены
потребителя.

## Последствия

### Польза

- Одна повторяемая процедура автономных запусков для любых проектов и агентов.
- Неизменяемость требований и сверка слайсов становятся именованными,
  проверяемыми правилами (`ATR-002`–`ATR-004`).
- Отклонение в одобрении коммитов записано с его прецедентом, а не живёт в
  истории чата.

### Компромиссы

- Навык добавляет обязательство по контрактам сценариев: пока
  `ai-standards-evals` не исполняет ATR-001/ATR-002, валидация только
  структурная.
- Деплой по адаптерам добавляет четыре файла шаблонов и записи реестра для
  сопровождения.

## Наблюдения

- [decision] Навык `autonomous-task-run` выпускается с гейтом на
  `autonomy-boundaries` и несёт entry gate, слайс-цикл со сверкой,
  неизменяемость требований, stop-условия и порядок приземления из issue
  #24.
- [decision] Требования task spec — абсолютная константа запуска: без
  дополнения, изменения и переинтерпретации; исправление, требующее любого
  из них, — stop-условие.
- [fact] Приняты две словесные адаптации ради переносимости и прецедента:
  «task spec (в проектах с ADR — в форме ADR)» и оговорка о стоящем одобрении
  коммитов.
