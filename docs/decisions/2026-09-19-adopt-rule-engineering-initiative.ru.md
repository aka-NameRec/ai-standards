# РЕШЕНИЕ: принять инициативу Rule Engineering

## Статус

- Принято

## Дата

- 2026-09-19

## Контекст

Proposal `docs/archive/20260917-000618-proposal-rule-engineering-skill-engineering-context-architecture-evals.md`
(заведён как issue #17) утверждает, что `ai-standards` должен стандартизировать,
как требуемое знание отбирается, размещается, загружается и проверяется, а не
максимизировать объём всегда загружаемого знания. В репозитории сейчас есть
один source-специфичный процесс нормализации (секция README `Import External
Rules`), нет формальной модели размещения, дисциплины валидации skills и
проверки на уровне поведения. Исполняемая eval-инфраструктура сознательно
вынесена в отдельную спецификацию `ai-standards-evals` (issue #18), чтобы
методология и инфраструктура могли приниматься или отвергаться независимо.
Пользователь принял направление инициативы, разделение объёма #17/#18 и
`docs/scenarios/` как дом контрактов сценариев 2026-09-19.

## Решение

Принять инициативу как пофазную работу в этом репозитории (фазы 0–9 в порядке
proposal), начав с фазы 0 (baseline) и фазы 1 (feature `rule-engineering`) на
ветке `rules-change/17-rule-engineering`:

1. Rule Engineering становится единственным универсальным процессом для любого
   нормативного правила независимо от источника; внешний импорт — один из его
   частных случаев.
2. Правило приемлемо только при выполнении свойств качества (atomic,
   unambiguous, actionable, properly scoped, observable, unique на уровне
   behavioral overlap, non-conflicting с явной precedence, правильный уровень
   абстракции, portable) и при хотя бы одной форме валидации.
3. Существующие правила массово не переписываются; внедрение инкрементальное.
4. Минификация `AGENTS.md` выполняется только после появления безопасного
   механизма маршрутизации и regression evals (фаза 8).
5. Контракты сценариев живут в `docs/scenarios/`; исполнение сценариев
   относится к `ai-standards-evals` (issue #18).

## Почему так

- Главный инвариант стандарта становится исполнимым: доставка нужной,
  однозначной, проверяемой инструкции в нужный момент, а не максимальный
  always-loaded объём.
- Единый процесс закрывает разрыв качества между внешними и внутренними правилами.
- Порядок фаз делает каждый следующий шаг зависимым от уже проверенных
  примитивов (baseline → rule engineering → traceability → dogfooding →
  модель размещения → контракт eval → skills → skill evals → минификация →
  cross-agent матрица).
- Разделение #17/#18 удерживает объём этого репозитория методологическим;
  инфраструктура исполнения не может быть отвергнута вместе с методологией и
  наоборот.

## Рассмотренные альтернативы

- Отклонить или отложить proposal: стандарты продолжают накапливать
  инструкции без пути проверки; отклонено пользователем.
- Переписать существующие правила сразу при внедрении процесса: высокий риск,
  нет базовой линии для сравнения; противоречит собственной
  последовательности proposal.
- Строить eval harness внутри этого репозитория: смешивает методологию с
  инфраструктурой; отклонено в пользу утверждённого разделения #17/#18.

## Последствия

- Польза: измеримый бар качества правил, требование наблюдаемого поведения для
  каждого нормативного правила, дисциплина размещения, которая позже
  обосновывает сокращение `AGENTS.md`, и пилотный путь через
  `standard-code-review`.
- Издержки и компромиссы: каждое будущее изменение правила становится более
  длинной, обдуманной процедурой; вся инициатива растягивается на несколько
  релизов; пины `feature_meta` (`2.5.0` для `rule-engineering`) должны
  оставаться правдивыми на момент релиза.

## Затрагиваемые модули

- `fragments/process/**` (новый `rule-engineering`; позже `context-architecture`)
- `registry.toml`, `ai.project.toml`, рендеренный `AGENTS.md`
- `templates/**` (позже: домен `skill-engineering`)
- `docs/scenarios/**` (позже: контракты сценариев)
- `docs/artifacts/**`, `docs/decisions/**` (записи инициативы)

## Инварианты и ограничения

- Никакой массовой перезаписи существующих правил в фазе 1.
- Shared policy остаётся vendor-нейтральной; механика harness — в адаптерах.
- Модульный контракт `ai-sync` не затрагивается: только контентные изменения
  поверх существующих входов.
- Контракты сценариев определяются здесь; исполнение сценариев — нет.

## Проверки

- Фазы 0–1 (эта ветка): baseline-артефакт записан; feature `rule-engineering`
  рендерится и покрыт тестами; `uv run pytest`, `uv run mypy scripts/`,
  идемпотентный `uv run ai-sync render --project-root .`,
  `uv run ai-sync doctor --project-root .` — ноль ошибок.
- Поздние фазы проверяются через собственные change plans и артефакты
  относительно записанной базовой линии.
