# Задача 30: устойчивость формата отчёта к смене провайдера модели

Английская версия: [30-report-format-stability.md](30-report-format-stability.md)

Доисследование issue #30, исполненное автономно (дисциплина
autonomous-task-run) на ветке `rules-change/30-report-format-stability`.
Триггер: регресс 2.10.0 показал устойчивые падения CR-010 (отчёт вне fenced
блока) и CR-011 (секция «Зависимости» вопреки drop-политике) на новом
провайдере инференса при том же идентификаторе модели, тогда как на
релизном пине 2.9.0 оба проходили; дифф ветки доказуемо не трогает ни один
файл code-review политики.

## Корневые причины

- **CR-010**: норма fenced-доставки (RVW-024) была анкорена на секцию
  `Report Shape` фрагмента, но текст фрагмента слова «fenced» не содержал —
  правило жило только в развёрнутом репортинг-референсе (`Destination`). На
  смещённом провайдере модель пропустила или обесценила пункт назначения и
  опубликовала обычный chat Markdown.
- **CR-011**: два конфликтующих сигнала — fallback-порядок фрагмента
  перечисляет `Dependencies` безусловно, а референс опускает её для
  самодостаточных изменений. Модель усреднила их в секцию-заглушку
  («новые зависимости не вводятся»), которую drop-политика считает padding,
  а не опусканием.

## Изменения

- `fragments/process/code-review.md`, `Report Shape`: fenced-инвариант
  заявлен в always-loaded фрагменте — весь отчёт (заголовки, находки, прозa)
  идёт внутри fenced Markdown блока, а обычный chat Markdown назван failure
  mode, для которого правило существует.
- `fragments/process/code-review.md`, fallback-порядок: `Dependencies`
  названа опускаемой для самодостаточных изменений — фрагмент выровнен с
  политикой секций референса.
- `templates/code-review-reporting.reference.md`: политика `Dependencies`
  получила анти-пример (заголовок со строкой-заглушкой — это padding, а не
  опускание); правило `Destination` называет требование «весь отчёт внутри
  fence» с failure mode.
- `rule_map.toml`: формулировка behavior `RVW-024` обновлена до более
  точного инварианта; `tests/test_ai_sync.py` фиксирует все новые фразы.

## Сознательные решения

- Семантика drop сохранена, а не смягчена до явной строки-заглушки:
  секция-заглушка — ровно тот padding, который запрещает no-padding-культура,
  и forbidden-исход CR-011 уже называет его. Анти-пример закрывает пробел
  интерпретации без изменения семантики нормы.
- Worked example сохраняет заполненную секцию `Dependencies`: он обязан
  показывать анатомию секции, когда она существует; drop-политика живёт в
  референсе по решению о размещении M4/M5.

## Проверка

- `uv run pytest` — 174 passed; `uv run mypy scripts/` — чисто;
  `ai-sync sync-templates` обновил развёрнутый референс.
- Поведенчески: CR-010 и CR-011, по три прогона каждый против этой ревизии
  ветки (kilo, glm-5.3-flash) — **6/6 PASS**
  (`ai-standards-evals: reports/issue-30/20261108-21*`): fenced-блок
  присутствует в каждом отчёте, секция-заглушка «Зависимости» не появилась
  ни в одном прогоне.

## Известное ограничение

- Кросс-провайдерные перегоны (старая конечная точка) из этого окружения
  неисполнимы: выбор провайдера живёт в конфигурации kilo пользователя.
  Завершение матрицы «оба провайдера» из issue #30 требует пользовательского
  прогона CR-010/CR-011 с прежним провайдером; ожидается, что правки выше
  держатся на обоих, поскольку failure mode теперь назван в always-loaded
  фрагменте.

## Наблюдения

- [факт] Пробел текста якоря RVW-024 (behavior описывал формулировку,
  которой во фрагменте не было) — конкретный образец риска дрейфа якоря,
  который policy-тесты не покрывают: они проверяют существование секции, а
  не наличие фразы behavior в ней.
- [решение] Выбрана формулировка анти-примера вместо смены семантики;
  отклонённый вариант записан в рабочем листе с обоснованием.
