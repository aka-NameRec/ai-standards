# Гид по гейту модульных контрактов

Английский источник истины: [module-contract-gate-usage.md](module-contract-gate-usage.md)

Гид описывает, когда включать фичу `module-contract-gate` и что она меняет для проекта.

## Зачем эта фича существует

Модульные контракты покрывались в двух точках: политика создания (`structured-artifacts`) и проверка на ревью (`code-review`, скилл стандартного ревью). Ничто не обязывало агента находить и применять контракты в момент написания кода, поэтому контракт мог существовать и при этом игнорироваться изменением, которое его нарушало, — ровно этот отказ закрывает фича. Обоснование и размещение: [решение о размещении](decisions/2026-08-28-module-contract-gate-feature-placement.md).

## Активация

Включите фичу в `ai.project.toml` — по договорённости сразу после `structured-artifacts`, чтобы раздел встал непосредственно после Module Contracts, — и выполните рендер:

```bash
uv run ai-sync render --project-root /путь/к/проекту
```

Фича — композит в реестре: она несёт и `structured-artifacts`, потому что гейт обнаружения без политики контрактов, которую он обслуживает, бессмыслен. Двойное включение дедуплицируется; включение гейта в проект, у которого вдруг не было политики контрактов, добавит и её.

## Что она меняет

Гейт — обязанность момента написания кода, а не проход ревью:

- **Discovery в начале задачи, пропорционально.** Одна дешёвая проверка устанавливает, объявляет ли проект контрактные артефакты вообще; заявленное отсутствие завершает discovery, и агент сообщает об этом одной строкой. Полную цену — запрос индекса и скан репозитория — платят только проекты, которые контракты объявляют; а когда индекса нет или он устарел, агент сообщает об этом до сканирования, так что цена становится решением, а не сюрпризом.
- **Покрытие по каждому затрагиваемому файлу.** Перед правкой агент решает, покрыт ли файл контрактом — по явному именованию, по каталогу, по потоку данных, по затрагиваемым обязанностям или по тестам, проверяющим поведение из контракта. Неясное покрытие трактуется как релевантное и читается.
- **Контракты ограничивают изменение.** Объём, допустимые изменения поведения, обработка ошибок, совместимость, требуемая проверка; изменение, противоречащее контракту, останавливается и репортится, а не реализуется молча.
- **Повторный discovery по триггерам.** Новый модуль или слой, движение контрактных файлов в diff, новые классы в наборе правок, сбои проверки, указывающие на непонятую границу.
- **Короткая контрактная заметка** в итоговом резюме реализации: что прочитано, что покрыто, сохраняет ли изменение контракт, что проверено против него.

Строгое правило остаётся абсолютным: ни одной правки производственного кода до завершения discovery по затрагиваемым файлам. Basic Memory удовлетворяет discovery только как индекс; канонические контракты читаются из репозитория.

## Чего она не делает

Она не создаёт контракты — политика создания остаётся в `structured-artifacts`, и у большинства модулей контракта по-прежнему нет и не нужно. Она не дублирует ревью: workflow code-review и скилл `standard-code-review` сверяют изменённые модули с контрактами постфактум — ровно это гейт дополняет. И она не затрагивает проекты, которые её не включили: обновление ai-standards для них ничего не меняет.

## Связь с workflow обновления

Скилл обновления (`update-ai-standards`) анонсирует эту фичу старым развёртываниям по маркеру `since` в `[feature_meta]` файла `registry.toml`, с рекомендацией относительно стеков проекта. Включение остаётся явным выбором проекта — в момент обновления или правкой манифеста напрямую.
