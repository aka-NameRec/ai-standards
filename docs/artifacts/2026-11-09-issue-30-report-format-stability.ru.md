# Рабочий лист: task spec доисследования issue 30

Английская версия: [2026-11-09-issue-30-report-format-stability.md](2026-11-09-issue-30-report-format-stability.md)

Task spec и рабочий лист Rule Engineering для issue #30, исполнение
автономное по дисциплине `autonomous-task-run`. Ветка
`rules-change/30-report-format-stability`; слияние в `main` — после
одобрения пользователем; push — только с отдельного согласования.

## Цель

Сделать нормы формата отчёта code review устойчивыми к привычкам
форматирования модели (наблюдается как сдвиг провайдера при том же
идентификаторе модели): правило fenced-доставки должно быть заявлено в
always-loaded фрагменте, к которому оно анкорится, а drop-политика
«Зависимости» — перестать конфликтовать с fallback-порядком фрагмента и
worked example.

## Вне объёма

- Никакого изменения семантики политики отчётности: `Dependencies` остаётся
  опущенной для самодостаточных изменений (строка-заглушка «явно указать
  отсутствие» остаётся запрещённой — это тот padding, от которого существует
  no-padding-культура).
- Никаких новых сценариев и никаких правок скореров в
  `ai-standards-evals`: контракты CR-010 и CR-011 и их механические оракулы
  уже фиксируют инварианты.
- Никакого релиза и push; слияние в `main` — только по явной инструкции.

## Наблюдения

- [факт] `RVW-024` анкорится на `Report Shape`, но текст фрагмента слова
  «fenced» не содержал — норма жила только в развёрнутом референсе; пробел
  текста якоря закрывается REQ-1.
- [факт] Fallback-порядок фрагмента перечисляет `Dependencies`
  безусловно, что конфликтует с drop-политикой референса; модель усредняет
  два сигнала — это и есть наблюдаемый отказ CR-011.
