# ПЛАН ИЗМЕНЕНИЙ: reference-режим рендеринга (issue #29)

Сессионный конверт для автономного прогона по этому плану: раздел Goal — цель, Scope — ограниченный объём работ, Non-goals и Invariants — архитектурные ограничения, Verification — план проверок, Stop Conditions и Checkpoints ограничивают исполнение, Expected Review Artifacts перечисляет, что человек ревьюит в конце.

## Goal

- Сделать так, чтобы каждый разумный заказ манифеста рендерился в `AGENTS.md` в пределах бюджета Codex на проектные доки (32 768 байт, дефолт `project_doc_max_bytes`) — переносом стеков и тяжёлых фич в reference-режим: полный текст деплоится управляемым reference-файлом, компактный pointer-блок рендерится инлайн. Decision record: `docs/decisions/2026-11-02-add-agents-md-progressive-disclosure.ru.md`.

## Scope

- В объёме:
  - схема манифеста/реестра для `reference_features` / `reference_stacks`
  - рендерер: сборка pointer-блоков, деплой reference-файлов, предупреждение о бюджете, вырезка provenance
  - контент: pointer-блоки для каждой вынесенной позиции; записи `INFRA_TEMPLATES` для их reference-файлов
  - переприцеливание `rule_map.toml` и policy-тесты
  - сценарии срабатывания триггеров в контрактах сценариев (`docs/scenarios/`, префикс `RD-*`) для каждой вынесенной позиции
  - релизная документация: README, CHANGELOG, анонс через `update-ai-standards`
- Вне объёма:
  - изменение существующих skill-пакетов и их активации
  - вывод вложенных per-directory `AGENTS.md`
  - поднятие или конфигурирование бюджета Codex
  - перенос фич сверх состава, зафиксированного в decision record (retrieval-routing и остальные фичи поведенческого ядра остаются инлайн)

## Touched Modules

- `scripts/ai_sync.py` (парсинг манифеста, `_resolve_fragment_ids`, `build_rendered_content`, таблицы деплоя шаблонов, `check`)
- `registry.toml`, `templates/project_manifest.toml`
- `fragments/**` (pointer-блоки авторятся рядом с вынесенными фрагментами; тела фрагментов не меняются)
- `templates/**` (источники управляемого деплоя reference-файлов по мере необходимости)
- `rule_map.toml`, `tests/test_rule_map.py`, `tests/test_ai_sync.py`
- `docs/scenarios/**` (новые контракты сценариев `RD-*`, EN + `.ru.md`)
- саморазвертывающийся `ai.project.toml` (первый потребитель: добавляет reference-списки)
- `README.md`, `CHANGELOG.md`, `meta.toml` (релизный бамп на релизном слайсе)

## Proposed Structure

- Манифест: `reference_features: list[str]`, `reference_stacks: list[str]`; валидация как у существующих списков, неизвестные имена дают `SyncError`.
- Реестр: метаданные возможности по каждой фиче/стеку, называющие источник pointer-блока (авторится рядом с фрагментом).
- Рендерер: для каждой позиции reference-режима фрагмент заменяется pointer-блоком; тело фрагмента деплоится в `.ai-standards/references/{stacks,features}/<name>.md` через `INFRA_TEMPLATES` с управляющим маркером и тем же гейтом фичи.
- Бюджет: именованная константа `AGENTS_MD_BUDGET_BYTES = 32768`; `render`/`check` предупреждают нефатально выше него.
- Provenance: блоки комментариев `Source provenance` вырезаются при сборке, как frontmatter сегодня.

## Flow

1. Контракт и доки: обновление модульного контракта `ai-sync` (этот слайс), актуальность decision record.
2. Слайс рендерера: схема манифеста/реестра + сборка pointer-блоков + предупреждение о бюджете + вырезка provenance; юнит-тесты на каждое поведение, включая байт-идентичный рендер для манифестов без новых ключей; прогон `uv run pytest`, `uv run mypy scripts/`.
3. Слайс контента: pointer-блоки для всех вынесенных позиций (8 фич + все стековые позиции реестра), записи деплоя `INFRA_TEMPLATES`; тесты рендерера расширяются по позициям.
4. Слайс карты правил: переприцеливание вынесенных правил через `source`, расширение `test_rule_map.py`.
5. Слайс evals: авторство контрактов сценариев `RD-*` по предложению ниже; реализация фикстур/scorers в `ai-standards-evals`; прогон regression suite; каждая вынесенная позиция зелёная до релизного слайса.
6. Релизный слайс: включение саморазвертывания, замер acceptance по размерам, README/CHANGELOG/версия/анонс, финальный рендер + чистый `doctor`.

## Предложение сценариев (контракт слайса 5)

Поведенческие сценарии следуют контракту формата сценариев; новый префикс `RD-*` группирует их; ID правил — `RD-001`/`RD-002` в `rule_map.toml` (см. слайс карты правил), ID сценариев начинаются с `RD-101`, чтобы пространства имён не пересекались. Каждый сценарий задаёт фикстуру, дословный промпт, ожидаемые наблюдаемые инварианты (активация подтверждается чтением reference-файла в трассировке раннера, затем корректное поведение оценивается против содержимого reference) и запрещённые исходы (действие без предварительного чтения; вопрос пользователю, где лежат правила; выдумывание правил).

- `RD-101` code-review: «голый» запрос ревью на диффе-фикстуре; инвариант: reference прочитан до любого вывода ревью; отчёт следует развёрнутой форме.
- `RD-102` basic-memory: операция над деревом знаний с последствиями reindex/masking; инвариант: reference прочитан до операций; запрещено: разрушительный шаг вразрез с reference.
- `RD-103` project-memory: продолжение работы между сессиями; инвариант: reference прочитан до записи/чтения `docs/local/**`; таксономия соблюдена.
- `RD-104` chroma: семантический поиск по коду; инвариант: маршрут через freshness-gate wrapper согласно reference; запрещено: запрос к устаревшему индексу.
- `RD-105` rule-engineering/skill-engineering: добавить правило в стандарты; инвариант: engineering flow выполнен, как изложен в reference (шаги потока, названная форма валидации).
- `RD-106` review-lenses: запрос с явным названием линзы; инвариант: трёхлинзовая модель применяется только в условиях её активации.
- `RD-107` knowledge-capture: запрос фиксации знаний; инвариант: decision/task-записи ложатся в определённые reference-файлом места.
- `RD-108` context-architecture: решение о размещении нового знания; инвариант: вопросы размещения отвечены по reference до выбора слоя.
- `RD-110` негативный зонд (сквозной): маленький баг-фикс на Python, не связанный ни с одной вынесенной темой; инвариант: задача выполняется на инлайн-ядре; запрещено: лишние чтения reference, блокировка на отсутствующем полном тексте.
- `RD-111` мульти-reference последовательность: задача, затрагивающая две вынесенные области (стековое правило + ревью); инвариант: оба reference прочитаны до действия.
- `RD-120` стековые триггеры (data-driven, по экземпляру на каждую стековую позицию реестра): стековая рабочая задача на фикстуре, кодирующей одно проверяемое правило из reference этого стека; инвариант: reference прочитан до правки; закодированное правило наблюдаемо в результате; запрещено: правка без предварительного чтения.

Поведение рендерера — юнит-тесты, а не поведенческие сценарии: наличие pointer-блока и путь, отсутствие тела фрагмента в рендере, вырезка provenance, срабатывание предупреждения при >32 768, байт-идентичный вывод без новых ключей, идемпотентность.

## Risks

- Комплаенс триггеров — поведение модели: вынесенная позиция, которую агенты игнорируют на практике, — тихая регрессия. Митигация: сценарии RD-* гейтируют релиз; упавший сценарий — свидетельство против дизайна, повод для ревью, а не тихого редизайна.
- Слишком слабая формулировка pointer-блока → провалы комплаенса; слишком сильная → чтения на нерелевантных задачах. RD-010 зондирует второй режим отказа.
- Дрейф реестра/манифеста у downstream-манифестов: update-ai-standards должен анонсировать новые ключи.
- Запас бюджета конечен (~5.2K на тяжёлом): новые фичи либо умещаются в инлайн-бюджет, либо поставляются в reference-режиме; предупреждение делает нарушения видимыми.

## Invariants

- Манифест без новых ключей рендерится байт-в-байт как до изменения.
- Рендер идемпотентен; frontmatter override-ов не протекает; управляющие маркеры соответствуют синтаксису назначения.
- Контент не генерируется: pointer-блоки и reference-файлы собираются из авторских источников.
- Фрагмент остаётся единственным источником истины и для инлайн pointer-блока, и для развёрнутого reference-файла.
- `SyncError` на неизвестные reference-имена, на загрузке, как на неизвестные фичи сегодня.
- Нефатальное предупреждение, никогда не жёсткий отказ, при превышении бюджета.

## Acceptance Criteria

- [ ] reference-рендеры light/mid/heavy измерены ниже 32 768 байт; средний заказ ~18.8K, тяжёлый ~27.6K.
- [ ] `uv run pytest` и `uv run mypy scripts/` чистые; идемпотентность и `doctor` чистые на саморазвертывающемся дереве.
- [ ] Каждый сценарий `RD-*` проходит в `ai-standards-evals` на ревизии-кандидате, включая негативный зонд.
- [ ] Саморазвертывающийся манифест рендерится с reference-режимом; размер рендера указан в релизных заметках.

## Verification

- Автоматическое: `uv run pytest`, `uv run mypy scripts/`, идемпотентность рендера, `ai-sync doctor`, regression suite `ai-standards-evals` (релизный гейт), замеры размеров по трём reference-манифестам.
- Ручное: вычитка pointer-блоков на точность триггеров (один проход ревью до релизного слайса).
- Наблюдаемость: вывод предупреждения о бюджете; отчёты evals в `ai-standards-evals/reports/`.

## Stop Conditions (сессионный конверт)

- Остановиться и запросить человеческое ревью, когда сценарий `RD-*` падает по дизайн-причине (недетерминированный триггер, неверная семантика reference), а не из-за бага фикстуры.
- Остановиться, когда слайс вскрывает потребность в новой абстракции, изменении публичного контракта сверх этого плана или изменении схемы `registry.toml`/`rule_map.toml`, не описанном здесь.
- Остановиться, когда локальные фиксы перестают сходиться внутри текущего слайса.
- Пуш и релиз всегда ждут явного человеческого одобрения.

## Checkpoints (сессионный конверт)

- После слайса 2: тесты рендерера зелёные, байт-идентичная обратная совместимость доказана, замеры размеров отчитаны.
- После слайса 4: карта правил согласована, policy-тесты зелёные.
- После слайса 5: полная матрица RD-* прогнана; упавшие сценарии ревьюятся с человеком до слайса 6.
