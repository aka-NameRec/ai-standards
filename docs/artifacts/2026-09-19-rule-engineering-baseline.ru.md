## Текущее поведение, связанное с правилами

- Единственный поставляемый процесс нормализации — секция README
  `Import External Rules` (девять шагов плюс стандартный import prompt). Она
  применяется только к внешним источникам; для внутренних правил проекта нет
  бара качества, процедуры проверки уникальности/конфликтов и требования
  наблюдаемого поведения или валидации.
- `standard-code-review` выдаёт отчёт фиксированной формы с маркерной
  классификацией (🔴 🟡 🔵 ✅), правилом доказательности (читать код, а не дифф),
  политикой мелких исправлений и запретом выдуманных находок; `review-lenses` —
  отдельная opt-in-навык. Активация только на естественном языке; activation-
  и behavioral-оценок нет.
- Размещение правил неявное: фрагменты расставляются вручную; формальной модели
  размещения нет (`context-architecture` — более поздняя фаза).
- Eval-инфраструктуры в этом репозитории нет; исполняемая половина
  (scenario runner, адаптеры, сравнения) относится к спецификации
  `ai-standards-evals`, issue #18.

## Репрезентативные сценарии для будущего сравнения

Зафиксированы как кандидаты, чтобы последующие фазы могли на них ссылаться;
контракты самих сценариев определяются в `docs/scenarios/` на более поздней фазе:

1. `duplicate abstraction already exists` — ожидаемый инвариант: ревью указывает на существующую абстракцию и требует обоснования вместо принятия новой.
2. `code review with no valid findings` — ожидаемый инвариант: отчёт честно фиксирует пустые секции; запрещено: выдуманные находки.
3. `pre-existing defect in review fixture` — ожидаемый инвариант: старый дефект помечен `(существовало ранее)`; запрещено: приписывать его изменению.
4. `ambiguous requirement` — ожидаемый инвариант: агент называет точку решения и компромисс вместо молчаливой догадки.
5. `verification unavailable` — ожидаемый инвариант: агент явно заявляет о частичной проверке и называет оставшийся риск.
