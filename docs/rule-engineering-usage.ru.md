# Руководство по Rule Engineering

Английская версия: [rule-engineering-usage.md](rule-engineering-usage.md)

Гайд описывает, когда включать feature `rule-engineering` и что он меняет в
проекте-адаптере.

## Зачем нужен этот feature

До сих пор единственным поставляемым процессом нормализации был поток импорта
внешних наборов правил: извлечь кандидатов, классифицировать как
`keep`/`adapt`/`reject`, нормализовать, разместить. Он применялся только к
внешним источникам. Правила, рождённые внутри проекта, правила, переписанные
со временем, и содержимое skills не имели бара качества: ни проверки
атомарности и однозначности, ни процедуры уникальности и конфликтов, ни
требования наблюдаемости или валидации. Rule Engineering заменяет этот
source-специфичный поток одним процессом для любого нормативного правила,
каков бы ни был его источник, а внешний импорт делает одним из его частных
случаев.

## Активация

Включите feature в `ai.project.toml` и выполните рендер:

```bash
uv run ai-sync render --project-root /path/to/project
```

Жёстких зависимостей у feature нет. Он естественно сочетается с `code-review`
(правила проверяются на наблюдаемое поведение) и с любой retrieval-возможностью
(подробные рекомендации живут в документации, а не в всегда загружаемом
контексте).

## Что он меняет

Процесс выполняется в момент создания и изменения правила:

- **Один поток для любого источника.** Внешние лучшие практики, внутренние
  находки проекта, rules reasoning/review/architecture/harness и содержимое
  skills проходят один и тот же инженерный поток; существующее правило снова
  проходит его при существенном изменении. Небольшая подтверждённая
  доказательствами правка формулировки полного потока не требует.
- **Девять свойств качества.** Atomic, unambiguous, actionable, properly
  scoped, observable, unique (проверяется на трёх уровнях пересечения —
  lexical, semantic, behavioral — решающий уровень behavioral), non-conflicting
  (с явной precedence, когда нужна), правильный уровень абстракции, portable.
- **Interpretation surface.** Формулировка выбирается так, чтобы минимизировать
  число существенных решений, которые агент вынужден додумывать между
  прочтением правила и его исполнением, — но не там, где задача действительно
  требует контекстного суждения.
- **Валидация обязательна.** Каждое правило определяет хотя бы одну форму:
  static validation, deterministic assertion, behavioral scenario, human
  rubric, cross-agent comparison. Правило без формы проверки в стандарт не
  попадает.
- **Размещение — часть инженерии.** Поток завершается выбором слоя, который
  доставляет знание в нужный момент: always-loaded rule, skill, skill
  reference, retrieval, script/tool, project knowledge или adapter.

## Чего он не делает

Он не переписывает существующие правила: внедрение инкрементальное, и при
включении feature существующее содержимое сохраняет поведение. Он не задаёт
формальную модель размещения — она появится вместе с планируемым feature
`context-architecture` — и никакую исполняемую механику форм валидации:
контракты сценариев будут жить в `docs/scenarios/` репозитория стандартов, а
исполнение сценариев относится к отдельной спецификации `ai-standards-evals`
(issue #18).

## Связь с Import External Rules

Поток импорта, описанный в README репозитория, становится частным случаем:
шаги извлечения кандидатов и нормализации остаются, но каждый кандидат теперь
проходит дальше — через свойства Rule Engineering, решение о размещении и
требование валидации — вместо остановки на «нормализовать и разместить».

## Связь с процессом обновления

Skill обновления (`update-ai-standards`) объявляет этот feature старым
развертываниям по маркеру `since` из `[feature_meta]` (`2.5.0`) в
`registry.toml`. Включение остаётся явным выбором проекта — при обновлении или
напрямую в манифесте.
