# Контракт формата сценариев

Английская версия: [scenario-format.md](scenario-format.md)

Контракт определяет структуру файлов поведенческих сценариев в `docs/scenarios/`
и требуемое поведение любого runner, который их исполняет (issue #17, фаза 5).
Сценарии проверяют, что стандарты дают наблюдаемое поведение, а не то, что
Markdown совпадает с прозой. Исполняемая механика — runner'ы, адаптеры
harness'ов, хранение результатов, матрицы совместимости — относится к
спецификации `ai-standards-evals` (issue #18); этот контракт —
стандартная сторона интерфейса, которую она потребляет.

## Раскладка файлов

- Один сценарий на пару файлов: `<ID>-<slug>.md` (английский) и
  `<ID>-<slug>.ru.md` (русская пара), где `ID` соответствует `<PREFIX>-<NNN>`
  (например `CR-001`). Префикс группирует сценарии по проверяемому feature
  (`CR-*` — code review).
- IDs сценариев стабильны: ID никогда не переиспользуется для другого
  сценария.
- Каждая ссылка на правило использует ID из `rule_map.toml` в обратных
  кавычках; policy-тесты проверяют, что каждый упомянутый ID существует.

## Обязательная структура

1. Frontmatter с `title` и `permalink`; заголовок повторяется как `# H1`.
2. Вводный абзац с областью feature, начинающийся `Behavioral scenario …`
   (EN) / `Поведенческий сценарий …` (RU), со списком `Verifies rules …` из
   ID правил, на которые сценарий нацелен, и строкой статуса (`draft`, пока
   формат не финализирован и сценарий не прогонен хотя бы раз).
3. `## Фикстура` — декларативное состояние до и дифф (или вход) под
   проверкой, описанные достаточно конкретно, чтобы runner мог их
   сконструировать.
4. `## Включённые features` — standards-features, отрендеренные при исполнении.
5. `## Prompt` — дословный prompt в кодовом блоке.
6. `## Ожидаемые наблюдаемые инварианты` — нумерованные инварианты, каждый с
   аннотацией ID правил, которые он закрепляет. Инварианты судят исход, а не
   формулировки.
7. `## Запрещённые исходы` — перечислимые режимы провала.
8. `## Scoring Rubric` — опционально; только там, где инвариант нельзя решить
   механически.
9. `## Наблюдения` и `## Связи` по правилам формы заметок knowledge tree.

Русская пара зеркалирует структуру локализованными заголовками; заголовок
`## Prompt` остаётся английским в обоих языках.

## Policy-тесты

`tests/test_rule_map.py` закрепляют механическую половину: имена файлов и
уникальность IDs, локализованные пары, обязательные заголовки на обоих языках,
кодовый блок prompt'а и разрешимость всех ссылок между `rule_map.toml` и этим
каталогом.

## Требуемое поведение harness

Соответствующий runner (спецификация в #18, реализация в `ai-standards-evals`)
обязан:

1. детерминированно конструировать фикстуру из декларативного описания
   сценария;
2. исполнять дословный prompt через адаптер harness с отрендеренными
   включёнными features;
3. фиксировать артефакт исхода (отчёт или ответ плюс события исполнения, где
   harness их даёт);
4. оценивать каждый ожидаемый инвариант и каждый запрещённый исход —
   механически, где возможно, и по scoring rubric, где неизбежно;
5. выдавать вердикты по сценариям и поддерживать cross-harness матрицу
   совместимости;
6. поддерживать сравнения baseline против candidate ревизий стандартов на
   идентичных сценариях.

Расхождение harness'ов на одном сценарии — находка для анализа: проблема
общего правила, проблема адаптера, ограничение harness или разброс модели.

## Наблюдения

- [fact] Инварианты судят исходы, а не формулировки: один и тот же сценарий должен проходить на любом harness, приходящем к тем же решениям.
- [fact] Контракт runner — только требуемое поведение; его реализация сознательно вне скоупа этого репозитория.
