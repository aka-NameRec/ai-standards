# Руководство по использованию retrieval-routing

Английская версия: [retrieval-routing-usage.md](retrieval-routing-usage.md)

Это руководство объясняет, как использовать фичу `retrieval-routing` из `ai-standards` в downstream-проектах.

`retrieval-routing` — инструментально-нейтральный policy-слой над всеми retrieval-capability: он определяет, когда агенту нужен retrieval, какой источник запрашивать, в каком порядке, когда переходить к более дорогому исследованию и как проверять найденное.

Ключевой принцип:

> Накопленное знание — не контекст разговора. Извлекай его, когда оно релевантно; не предзагружай только потому, что оно существует.

## Цели

Включайте `retrieval-routing`, когда хотите, чтобы агент или команда:

- перестали предзагружать обширную историю только потому, что она доступна
- обращались к самому узкому источнику знания, способному ответить на текущий вопрос
- маршрутизировали вопросы по информационной потребности, а не по привычности инструмента
- относились к результатам retrieval как к зацепкам, всё равно требующим верификации
- эскалировали постепенно, а не сканировали репозиторий без разбору

Типичные результаты:

- меньшие и лучше прицеленные контекстные окна
- меньше ложных выводов из непроверенных попаданий памяти
- предсказуемое использование включённых retrieval-capability
- канонические источники по каноническим вопросам

## Что покрывает фича

Фича стандартизует общую политику для:

- retrieval до широкой разведки
- использования включённой retrieval-capability, когда она совпадает с информационной потребностью
- маршрутизации по потребности (project memory, каноническая документация, семантический поиск по коду, прямой доступ к исходникам, структурная code intelligence, финальная верификация)
- retrieval как обнаружения улик, а не доказательства
- верификации на авторитетном слое
- постепенной эскалации: узкий retrieval → широкий retrieval → точечное чтение файлов → инспекция всего репозитория

Сознательно не стандартизуется:

- API-команды конкретных инструментов (Basic Memory, Chroma, graph-инструменты)
- какие backend'ы проект обязан разворачивать
- управление индексами, свежесть, конфигурация эмбеддингов (это зона фич-реализаций: `basic-memory`, `chroma`, `structural-code-intelligence`)

## Capability и Implementation

Capability именуются независимо от инструментов-реализаций:

| Capability | Типичная реализация |
|---|---|
| project memory | Basic Memory (или просто файлы в `docs/local/**`) |
| semantic code search | Chroma |
| structural code intelligence | graph-инструмент (экспериментально) |

Смена backend'а не должна требовать переписывания поведенческих правил. `retrieval-routing` корректно работает с одним включённым backend'ом и вовсе без них: без backend'ов таблица маршрутизирует к канонической документации, прямому доступу к исходникам и тестам.

## Таблица маршрутизации

| Информационная потребность | Предпочтительный источник |
|---|---|
| состояние предыдущей задачи, локальные решения, обнаруженные паттерны проекта, незакрытые исследования | project memory (локальная рабочая память) |
| канонические решения, архитектура и доменные правила | Git-отслеживаемая документация в `docs/domain/**`, `docs/decisions/**`, `docs/architecture/**` |
| семантическое обнаружение кода, аналогичные реализации, неизвестное место реализации | semantic code search (Chroma) |
| точный символ или файл уже известны | прямой доступ к исходникам |
| пути вызовов и зависимостей, анализ влияния между модулями | structural code intelligence (когда включена) |
| финальная верификация | каноническая документация, исходный код и тесты |

## Осведомлённость о capability

В начале нетривиальной разведки агент определяет, какие включённые retrieval-capability совпадают с задачей, прежде чем выбирать стратегию исследования. Он не вызывает каждую capability ритуально: определи информационную потребность, определи совпадающую включённую capability, используй её, когда она способна существенно сузить поиск.

## Навык развёртывания

При включённой `retrieval-routing` и объявленных агентах `ai-sync sync-templates` распространяет на них навык/команду/правило `deploy-ai-retrieval-stack`. Навык разворачивает включённые в манифест retrieval-слои (Basic Memory, Chroma) в свободном от гонок порядке.

## Связь с другими фичами

- `basic-memory` реализует capability project-memory над Markdown-знанием.
- `chroma` реализует capability semantic-code-search над исходными файлами.
- `structural-code-intelligence` (экспериментальная) реализует структурную capability.
- `session-hygiene` определяет, когда состояние должно сохраняться и перезагружаться; `retrieval-routing` — как оно извлекается.
- `agent-usage-hygiene` разделяет цель экономии контекста со стороны использования.
- `module-contract-gate` держит канонические контракты в артефактах репозитория; retrieval может их только находить.

## Пример манифеста

```toml
features = [
  "retrieval-routing",
  "basic-memory",
  "chroma",
  "structured-artifacts",
]
```

## Практические рекомендации

- Включайте `retrieval-routing` в каждый проект, где есть хоть одна retrieval-capability; это связующий policy-слой.
- Считайте попадания памяти гипотезами: при значимой корректности подтверждайте по исходникам.
- Не расширяйте разведку рефлекторно при первом промахе точечного запроса; эскалируйте по одному шагу.

## Observations

- [fact] Политика инструментально-нейтральна: она называет capability, а не API инструментов, поэтому смена backend'а не переписывает поведение.
- [fact] Таблица маршрутизации направляет финальную верификацию к канонической документации, исходникам и тестам — но не к retrieval-индексам.
