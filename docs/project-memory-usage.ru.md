# Руководство по использованию project-memory

Английская версия: [project-memory-usage.md](project-memory-usage.md)

Это руководство объясняет, как использовать фичу `project-memory` из `ai-standards` в downstream-проектах.

`project-memory` даёт локальной межсессионной рабочей памяти стандартный дом и жизненный цикл: `docs/local/**`, по умолчанию в `.gitignore`, с фиксированной таксономией, политикой записи, политикой чтения и явным путём продвижения в каноническую документацию.

## Цели

Включайте `project-memory`, когда хотите, чтобы агент или команда:

- сохраняли состояние задачи между сессиями, не загрязняя историю Git и канонические документы
- возобновляли вчерашнюю задачу с компактной точки входа вместо проигрывания чата
- держали предварительные решения и исследования отдельно от принятых проектных решений
- фиксировали обнаруженные паттерны проекта как рабочее знание, которое можно заменить

Типичные результаты:

- каноническая документация свободна от сессионного состояния
- новая сессия стартует с точечного запроса, а не со свалки памяти
- предварительное знание имеет видимый статус и явный путь продвижения

## Области памяти

| Область | Путь | Канонична? | Коммитится? |
|---|---|---|---|
| каноническое знание проекта | `docs/domain/**`, `docs/decisions/**`, `docs/architecture/**` | да | да |
| локальная рабочая память | `docs/local/**` | никогда | нет (по умолчанию в `.gitignore`) |

Отсюда два жёстких правила:

- Никогда не считать локальную рабочую память канонической документацией проекта.
- Не записывать временное состояние задачи, спекулятивные находки или данные продолжения сессии в каноническую документацию лишь ради сохранения контекста агента.

## Таксономия

| Категория | На какой вопрос отвечает | Жизненный цикл / поля |
|---|---|---|
| `context/` | что мы пытаемся сделать | goal, scope, constraints, phase, next |
| `decisions/` | что решено локально и почему | `provisional` → `confirmed` → `superseded` / `rejected` |
| `progress/` | где остановилась работа | `done`, `current`, `blocked`, `next` |
| `patterns/` | какое переиспользуемое свойство обнаружено | валидируется по исходникам; заменяется при противоречии |
| `investigations/` | что исследуется, какие есть улики | `open` → `resolved` / `abandoned` |
| `handoffs/` | как возобновить без проигрывания чата | goal, confirmed state, open questions, next action |

Семантические категории стандартны; физическое разбиение на каталоги может настраиваться проектом.

Локальное решение со статусом `confirmed` означает «подтверждено в контексте текущей работы». Оно автоматически не становится канонической записью решения.

## Политика записи

Память — курируемое хранилище состояния, а не журнал исполнения.

Записывайте, когда информация: понадобится в следующей сессии; существенно влияет на дальнейшие решения; дорога в восстановлении; является результатом исследования; объясняет текущий статус; фиксирует нерешённый вопрос или блокер; или является подтверждённым переиспользуемым паттерном проекта.

Не записывайте: то, что и так говорит один очевидный файл; вывод инструментов; детали рассуждений; то, что уже существует канонически; догадку без полезной роли; дубль, не меняющий состояния.

## Политика чтения

Запрашивайте локальную память по текущей цели, релевантным сущностям, модулям, концепциям, решениям и идентификаторам задач — никогда `read docs/local/**` на старте сессии. Для продолжения прежней работы: извлеките релевантный context, затем текущий progress, затем релевантные decisions; patterns и investigations открывайте только по мере нужды текущего шага.

## Продвижение

Продвижение из локальной памяти в каноническую документацию — явная семантическая операция, а не автоматическая синхронизация:

```text
capture → retrieve/update → validate → discard | retain local → promote? → canonical docs
```

Продвигайте только знание, ставшее устойчивым, и только когда пользователь или workflow проекта разрешает соответствующий канонический артефакт. Например, `docs/local/decisions/catalog-indexing.md` может со временем стать `docs/decisions/2026-09-18-incremental-catalog-indexing.md` — после валидации и по явному запросу пользователя.

## Форма заметок и doctor

Минимальный frontmatter: `title`, `type`, `status`, `updated`, плюс `source`, когда заметка фиксирует обнаруженный факт. Требования к каноническим заметкам — датированные имена файлов, секции `## Observations` и `## Relations` — не применяются внутри `docs/local/**`.

`ai-sync doctor` аудирует локальную область ослабленными правилами (только читаемость) и предупреждает, когда область существует без покрывающего паттерна `.gitignore` (`local-memory-not-gitignored`). При включении фичи добавьте `/docs/local/` в `.gitignore`.

## Связь с другими фичами

- `retrieval-routing` маршрутизирует запросы «состояние предыдущей задачи» и «локальные решения» в эту память.
- `basic-memory` — рекомендуемый retrieval-слой над областью; фича работает и без него (просто файлы) — это и есть разделение capability/implementation.
- `session-hygiene` определяет, когда состояние сохранять и перезагружать; `project-memory` — что именно и как.
- `structured-artifacts` владеет reviewable-каноническими артефактами; продвижение из локальной памяти следует его политике записи.
- `knowledge-capture` синхронизирует локальные context/progress/handoff в рамках стандартного захвата знаний.

## Пример манифеста

```toml
features = [
  "retrieval-routing",
  "basic-memory",
  "project-memory",
  "structured-artifacts",
  "session-hygiene",
]

# Опционально: перенести локальную область внутри дерева знаний.
# [project_memory]
# local_tree = "local"
```

## Observations

- [fact] Таксономия и жизненный цикл инструментально-независимы; их удовлетворяют простые файлы в `docs/local/**`, а `basic-memory` добавляет точечный поиск поверх.
- [fact] `doctor` ослабляет канонические правила внутри локальной области и предупреждает, когда область не в `.gitignore`, поэтому локальная память и каноническое знание не смешиваются незаметно.
