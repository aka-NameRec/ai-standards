# Руководство по применению code-review

Англоязычный оригинал: [code-review-usage.md](code-review-usage.md)

Это руководство о том, когда браться за возможность `code-review` и как она соотносится с остальными механизмами качества в `ai-standards`.

Формат отчёта здесь сознательно не пересказывается. Он задан один раз — заполненным примером в [templates/code-review-report.md](../templates/code-review-report.md), так что читать его нужно ровно в одном месте и менять тоже в одном.

## Зачем нужна эта возможность

Без неё голый запрос «сделай code review» каждый раз даёт разную форму и разную глубину проверки — в зависимости от инструмента, модели и сиюминутной формулировки. `code-review` фиксирует это, перенося триггер, проверяемые аспекты и форму отчёта в собранные инструкции проекта, вместо договорённости внутри чата.

Это не замена тестам, линтерам, проверке типов или ревью человеком. Это стандартный способ попросить агента о структурированном повторном проходе.

## Активация

Включите фичу в `ai.project.toml` и выполните обе команды:

```bash
uv run ai-sync render --project-root /path/to/project
uv run ai-sync sync-templates --project-root /path/to/project
```

`render` помещает правила в `AGENTS.md` (или в мост `CLAUDE.md` для Claude Code); `sync-templates` раскладывает заполненный пример в `.ai-standards/code-review-report.md`, на который правила ссылаются. Канал раскладки agent-agnostic, поэтому не нужны ни slash-команда, ни отдельный skill, ни adapter в `tooling.agents` — поведение одинаково в Claude Code, Codex, Cursor и любом другом инструменте, читающем сгенерированный файл инструкций.

Если `sync-templates` пропустить, агент сообщит, что примера нет, и откатится к порядку разделов, названному во фрагменте, — отчёт деградирует, а не ломается.

Триггером служит голый, ничем не уточнённый запрос: `code review`, `сделай ревью`, `проверь код`, `review this` и подобные. Если запрос уже сужает область, режим или ракурс — например, явный вызов `review-lenses` или «просто проверь на баги» — приоритет у него.

## Что покрывает ревью

Пять аспектов в порядке приоритета: Correctness, Architecture & Conventions, затем Reuse, Quality и Efficiency. Корректность и конвенции идут первыми, потому что ревью, начинающееся с предложений по чистке и пропустившее реальный баг, бесполезно.

Что именно попадёт в отчёт, определяют два правила — оба существуют ради доверия к выводу, а не ради его объёма:

- **Доказательность.** Находке нужна конкретная локация в файле и названное нарушенное правило. Без любого из двух она не сообщается. Это соответствует публичным рекомендациям по промптингу из продакшн-пайплайнов AI-ревью (источники — в decision record проекта), которые поощряют подкреплённые доказательствами замечания и штрафуют спекулятивные.
- **Без раздувания.** Меньше находок с высокой уверенностью лучше, чем полный на вид список. Честно пустой раздел — лучший исход, чем выдуманная придирка.

Проблемы, существовавшие до текущего diff, всё равно сообщаются с пометкой `(pre-existing)`, чтобы не читаться как обвинение текущего изменения. Сообщение о такой проблеме не обязывает её исправлять — решение остаётся за автором, и её можно завести как follow-up вместо расширения патча.

## Связь с Review Lenses

`code-review` и `review-lenses` дополняют друг друга, и проект может включить любую из двух или обе:

| | `code-review` | `review-lenses` |
|---|---|---|
| Активация | автоматическая, на обычный запрос | явная, по названию workflow или его адаптера |
| Область | корректность и конвенции плюс чистка | только чистка (Reuse / Quality / Efficiency) |
| Вывод | фиксированная форма отчёта | находки, сгруппированные по ракурсам |
| Когда уместна | интерактивное ревью в чате | осознанные проходы чистки и CI |

Включение `review-lenses` не меняет поведение голого запроса «code review», а явный запрос прохода review-lenses не идёт через форму отчёта `code-review`. Собственные рекомендации и adapter-шаблоны — в [review-lenses-usage.ru.md](review-lenses-usage.ru.md).

## Интеграция с CI

Для автоматизированного, неинтерактивного ревью предпочитайте `review-lenses` в режиме `review-only`: он уже задокументирован именно для этого и поставляется с adapter-шаблонами. Оставляйте `code-review` для интерактивных сессий, где разработчик сам печатает запрос.

## Связь с другими механизмами качества

`code-review` дополняет, а не заменяет ревью человеком, детерминированные линтеры и проверку типов, тесты и собственные архитектурные, error-handling и стековые правила проекта — с которыми этот workflow сверяется, а не повторяет их.
