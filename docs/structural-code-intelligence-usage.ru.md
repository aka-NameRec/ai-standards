# Руководство по использованию structural-code-intelligence

Английская версия: [structural-code-intelligence-usage.md](structural-code-intelligence-usage.md)

Это руководство объясняет, как использовать фичу `structural-code-intelligence` из `ai-standards` в downstream-проектах.

`structural-code-intelligence` — **экспериментальная** capability: retrieval по связям между сущностями кода — путям вызовов, путям зависимостей, границам модулей, анализу влияния. Она не входит в рекомендуемый стек; включайте её осознанно, после того как приведённая ниже методология evaluation подтвердит её пользу для проекта.

## Цели

Включайте `structural-code-intelligence`, когда проекту нужны:

- запросы путей вызовов и зависимостей по большой кодовой базе
- анализ влияния изменения, охватывающего несколько модулей
- обход архитектуры без чтения каждого файла
- проверка структурных утверждений («что от чего зависит»), на которые grep не отвечает точно

Типичные вопросы: кто это вызывает; что зависит от этого модуля; какой путь соединяет endpoint X с персистентностью Y; что может затронуть изменение класса Z.

## Контракт маршрутизации

Предпочитайте structural code intelligence, когда вопрос в первую очередь о связях между известными или находимыми сущностями кода, а не о семантическом сходстве. Семантическое обнаружение («где реализовано ценообразование?») маршрутизируется в Chroma; вопросы связей («что затронет изменение этого класса?») — сюда. Полную таблицу владеет `retrieval-routing`.

Структурные результаты сужают множество кандидатов; они не доказывают полноту. Исчерпывающие или критичные к корректности утверждения требуют точного поиска плюс сборки, типизации или статических проверок, а финальная верификация происходит на авторитетном слое — канонической документации, исходном коде и тестах.

- Нейтральность к реализации

Capability не называет инструмент: её реализует graph-инструмент (Graphify — один из возможных backend'ов, проверен на большой backend-кодовой базе ~9k узлов / ~23k рёбер), и стандарты никогда не кодируют команды конкретного инструмента. Обновляйте структурный индекс перед запросами связей — событийно, как и остальные retrieval-индексы: после VCS-операций и структурных изменений, но никогда как ритуал сессии.

Структурный граф описателен: он фиксирует, чем код структурно является. Модульный контракт нормативен: он утверждает, чем код должен быть. Граф может генерировать или валидировать module maps и проверять объявленные факты контрактов, но никогда не заменяет контракт.

## Почему экспериментальная

Включение в рекомендуемый стек ждёт evaluation A/B/C на реальных инженерных задачах — см. [structural-code-intelligence-evaluation.ru.md](structural-code-intelligence-evaluation.ru.md). До тех пор фича поставляется для проектов, которые хотят прогнать evaluation на своей кодовой базе.

Принимайте графовую инфраструктуру только если её измеренное улучшение на релевантных инженерных задачах оправдывает стоимость развёртывания и сопровождения.

## Связь с другими фичами

- `retrieval-routing` маршрутизирует сюда вопросы связей и требует верификации на авторитетном слое.
- `chroma` отвечает за семантическое обнаружение; они дополняют друг друга, не пересекаясь.
- `module-contract-gate` держит контракты каноническими; граф может лишь сверять объявленные факты с реальностью.
- `structured-artifacts` владеет module maps, которые структурный backend может генерировать или валидировать.

## Пример манифеста

```toml
features = [
  "retrieval-routing",
  "chroma",
  "structural-code-intelligence",  # experimental — включать осознанно
]
```

## Observations

- [fact] Capability нейтральна к реализации: стандарты не называют инструмент, поэтому graph-backend можно заменить, не переписывая поведенческие правила.
- [fact] Она сознательно отсутствует в рекомендуемом стеке, пока evaluation A/B/C не подтвердит включение.
